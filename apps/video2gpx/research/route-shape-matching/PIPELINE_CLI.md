# rsm.pipeline: video + area → GPX (frozen command for the app)

One command packages the research chain (FINDINGS.md): vms motion → far-feature rotation → local OSM graph → dense HMM with a wide f_eff × kappa scan → 19 decoys → anchors and RTS fusion (variant (d)) → driving line → GPX. No hand-set value per video. Provisional thresholds are marked and come from the four development videos only. Frozen configuration and code hash: `rsm/pipeline/frozen.json`.

```
python -m rsm.pipeline run --video V --bbox S,W,N,E --pbf <local .osm.pbf> --out DIR
        [--vehicle auto|bike|motorcycle|car] [--bike-paths off|on|fallback] [--offset-m 1.5] [--start-time ISO8601] [--traffic-side auto|left|right] [--decoys 0|N|19] [--resume]
        [--start-bbox S,W,N,E] [--end-bbox S,W,N,E] [--start-tol-m 150] [--hint FILE.gpx|kml] [--hint-buffer-m 300] [--hint-fallback auto|off]   # area hints, see below
        [--anchors FILE.json] [--from-step STEP]   # user anchors and rerun from a step, see docs/USER_ANCHORS.md
python -m rsm.pipeline version                                                   # {"type":"version","version","code_hash"} of the frozen pipeline (frozen.json)
python -m rsm.pipeline retime DIR --start-time 2026-05-01T08:30:00+02:00        # rewrites <time> in route.gpx only, no recompute
python -m rsm.pipeline.freeze                                                    # regenerates frozen.json (config + code hash)
python -m rsm.pipeline export --out DIR --dest FILE.gpx --summary FILE.json [--dem-dir DIR] [--fps 50] [--trim auto|off] [--start-time ISO] [--title T] [--link URL] [--app-version V]   # Incyclist GPX, see below
python -m rsm.pipeline profile --out DIR --dest FILE.json [--dem-dir DIR]          # elevation along the whole decoded path (app Höhe stage and playback view); also writes elevation_diag.json next to FILE.json
python -m rsm.pipeline inspect-series --out DIR [--dest FILE] [--window-m 30]    # read only: per-second series of a finished run and its weak stretches with causes (app Analyse stage); default FILE OUT/inspect/series.json
python -m rsm.pipeline inspect-frame --out DIR --t SECONDS [--video FILE] [--what motion,rotation]   # read only: the points tracked for the frame pair and far-feature window at video time T
python -m rsm.pipeline dem-plan --out DIR [--dem-dir DIR] [--sources a,b]         # extra elevation blocks the route needs, offline (see "Elevation sources")
python -m rsm.pipeline dem-fetch --out DIR [--dem-dir DIR] [--sources a,b]        # download them (progress events), see "Elevation sources"
```

- `--bbox S,W,N,E` (degrees) is the search area, used **exactly** (edges whose middle lies inside; ways are read whole). The `.osm.pbf` is read in place, never copied, no network.
- `--decoys N`: size of the optional plausibility test (default **0 = off**: step 5 is reported `skipped`, the verdict comes from the decoy-free rule below; 19 = the full test; 1–18 = the first N decoys in the order foreign, mirror, foreign+shuffle, shuffle). The decoy test costs about as much as all other steps together (Roanne, 44 min video: about 2.5 min per decoy at first, 40 min for 12 decoys), which is why it is off.
- `--vehicle auto` (default) estimates the vehicle from the video (soft prior). `--bike-paths` adds cycleways, paths and tracks for a bike (see "Bike paths"). `--offset-m` overrides the driving-line offset. `--traffic-side auto` derives the side from the bbox centre.
- `--resume`: keep finished steps whose inputs are unchanged (see Resume). Without it, a run starts from scratch in DIR.
- `--from-step STEP` (needs `--resume`): the steps before STEP are reused as they are (even if their inputs changed: a warning is logged; exit 2 if one has no result), STEP and all later steps are computed again. The app starts every run with `--resume` and offers "Ab Schritt … neu berechnen".
- `--anchors FILE` (or inline JSON): user anchors `[{"t": s, "bbox": [S,W,N,E]}]`: at video time t the camera is inside the frame. Hard per-step masks of every HMM decode from route_search on (`rsm/pipeline/anchors.py`); anchors no route can satisfy together are dropped, logged and reported (status `user_anchors`, `route.pkl` / summary key `anchors` = {n, used, dropped, dropped_t}). They enter the hashes from route_search on (params key `anchors`); a frame outside `--bbox` grows the search area (+500 m, the map step reruns). See docs/USER_ANCHORS.md.
- `retime` needs a finished run; `--start-time` is any ISO 8601 time (offset allowed), written as UTC. Default for `run` is `2000-01-01T00:00:00Z`.

## Area hints (start / end frame, route hint)

Optional knowledge about the video; without these options nothing changes (same results, same checkpoint hashes, so old projects resume).

- `--start-bbox S,W,N,E`: the route must **begin** inside this frame. A hard constraint on the initial HMM state: the initial score of every cell whose centre is outside the frame (grown by `--start-tol-m`, default 150 m, because the first seconds may be gaps) is −inf, in the calibration scan, the decode and the posterior (route search and refine). `--end-bbox` does the same for the final state (back-trace from end cells inside the frame only, backward message starts there). Both must intersect `--bbox` (exit 2 otherwise).
- `--hint FILE`: a `.gpx` (every `trkseg` and `rte`) or `.kml` (`LineString`, `gx:Track`, inside `MultiGeometry` / `Folder`). Only the geometry counts: timestamps are ignored, the direction is not trusted (both directions stay possible), the hint is never GPS truth. Unreadable files, files without a line, a hint outside `--bbox` and a buffer outside 100 m to 2 km exit with code 2.
- **map step:** keeps the edges within `--hint-buffer-m` (default 300 m) of the hint, plus the shortest road connections (up to max(2 km, 5 buffers)) between separate pieces of the corridor, so the road set stays connected. Graph and the full edge set of the box stay (`map/edges_real.npy` = corridor, `map/edges_full.npy` = whole frame, for the fallback). Status `hint_corridor`: corridor road km (undirected) against the vms nominal length × the lowest distance scale (0.8) = the shortest route the corridor must hold; `good` ≥ 1.2×, else `difficult`. No road in the corridor: status `problem`, hint ignored, whole frame used (`--hint-fallback off`: exit 4).
- **route_search:** with frames, a start or end that no route can satisfy (empty frame, unreachable) gives a `start_frame` / `end_frame` status `problem` ("frames are ignored for this run") and the same search unconstrained. With a hint and `--hint-fallback auto` (default): if the corridor result is not `confident` (verdict without decoys), route_search runs **once more on the full search frame** (progress restarts at 0 %, phase `fallback`), keeping the start/end frames; the better result wins (higher verdict, then higher score per km), and `hint_corridor` says which (`route_search/hints.json`, summary `hints_used.hint`). `--hint-fallback off`: corridor result only. If the full frame is too large for the HMM memory cap, no fallback is possible (logged).
- **Status signals (new):** `start_frame` (value = metres the decoded start lies outside the frame; `good` inside, `difficult` within the tolerance, `problem` frame ignored), `end_frame` (same for the end), `hint_corridor` (see above; after the search it also reports corridor used / fallback used), `hint_agreement` (value = share of the decoded route within the buffer of the hint; information only: `good` ≥ 0.8).
- **Checkpoint hashes:** the hint file (content hash) and buffer enter the `map` hash only when a hint is given; frames, tolerance and hint fallback enter the `route_search` hash only when given. So a changed hint reruns from `map`, a changed frame from `route_search`, and runs without hints keep their old hashes.
- **Result:** `result.summary.hints_used` and `project.json: hints_used` = `{start_bbox, end_bbox, frames_applied, tol_m, hint_file, buffer_m, route_hint_applied, fallback_used, hint:{corridor_verdict, full_verdict, chosen, agreement, ...}, notes}` (null without hints); the GPX metadata carry `rsm:with_hints`, `rsm:route_hint` (file, buffer_m, applied, fallback_used), `rsm:start_frame` / `rsm:end_frame` (bbox, tol_m, applied) and `rsm:pipeline_hash`. `project.json` and the result also carry `pipeline_hash` (the code hash of `frozen.json`).
- Roanne check (resumed from the finished motion and rotation, warm cache; truth = GPS, scoring only): (a) no hints: identical route to before (0.0 m), 108 s route_search; (b) start frame 2 x 2 km: confident, same route, 112 s; (c) coarse hint (20 points, +80 m), 300 m corridor: confident, correct road 100 %, along-track error median 3.6 m, map 4.2 s, route_search 4.2 s; (d) wrong hint (another valley road, 25 km): corridor result no_route, fallback on the full frame confident and correct (route_search 116 s in total, `fallback_used`).

## Adaptive calibration grid

The scan grid is f_eff 250-600 x kappa 0.8-3.5. If the best cell lies on an edge, route_search extends that edge by 2 rows / columns of the same log ratio (hard limits f_eff 150-900, kappa 0.5-7; kappa below the scan only if the HMM memory rule allows it), repeating at most 3 times; then the local refinement runs around the new peak. A grid that was not extended behaves exactly as before. `calibration_peak` reports the extension ("scan grid extended to f_eff a-b, kappa c-d") and stays `difficult` / `problem` if the peak is still at a hard limit. Not done: the far-feature focal seed in the rotation step. The decoy test (`--decoys`) still scans the base grid only. First Madone retest (motorcycle, 51 min, no hints): the peak kept moving to f_eff 148 / kappa 6.6 (hard limit) and the route stayed in Nice (verdict no_route), so the extension alone does not fix that video; the start-frame and hint cases were not finished.

## Steps (APP_SPEC section 4)

| # | id | what | percent is |
|---|---|---|---|
| 1 | `motion` | vms optical-flow motion (vendored `rsm.pipeline.vmsx`), usable share, nominal length, area check | frame pairs done / total (+ horizon calibration at 0 %) |
| 2 | `rotation` | far-feature yaw (4 processes), yaw series, heading tracks, vehicle estimate | tracking chunks of 120 s done / total, then series |
| 3 | `map` | density map of the pbf, automatic decoy boxes, one extraction pass, road graphs, memory pre-check | bytes of the pbf read (read, filter), graphs built |
| 4 | `route_search` | wide scan f_eff 250–600 × kappa 0.8–3.5, local refinement, Viterbi decode, posterior | HMM runs done / total (88 coarse + 15 refinement), then decode and posterior phases |
| 5 | `plausibility` | OPTIONAL (`--decoys N`, default off = `skipped`): N decoys on the same scan, rank, margin, verdict | decoys done / 19, with the runs inside the current decoy |
| 6 | `refine` | posterior mean and spread, curve anchors, quality gate, robust RTS fusion, one position per second | forward / backward passes of the path posterior, then phases |
| 7 | `gpx` | driving line, GPX, route points, project file | phases |

Each step runs as a subprocess `python -m rsm.pipeline _memguard --max-gb 12 --min-free 25 -- python -m rsm.pipeline _step <id> --dir DIR` (a frozen copy of `tools/memguard.py`: the group is killed above 12 GB resident or below 25 % system-free memory; also when the sidecar dies). Heavy pools use at most 4 workers. One step at a time.

## Fixed rules

- **Area.** Exactly the user's bbox. Road classes by vehicle (one rule per class; chosen in step 3 after the vehicle is known):
  - car, motorcycle: `motorway trunk primary secondary tertiary unclassified` + `_link` (the Amalfi setup, no residential);
  - bike: `trunk primary secondary tertiary unclassified residential living_street` + `_link`, no motorway (the setup of the three bike videos).
  `area=yes` and `access=private` ways are dropped. Tunnels and bridges are kept.
  - **bike paths** (maintainer decision 2026-11-13, **off by default**, see "Bike paths" below): `cycleway path track` (+ `service footway pedestrian bridleway` with a bicycle permission) only for `--vehicle bike` (in the search map) or as the fallback of an estimated bike (`--vehicle auto`) whose road result is not confident. Motorcycle and car never.
- **Area check** (after step 1): ratio q = nominal vms length × 3.5 (the upper distance scale) / bbox diagonal; `good` q ≤ 1.5, `difficult` ≤ 3, else `problem`. After step 4 a second `area_size` status reports how long the route stays within 300 m of the bbox edge (good ≤ 5 %, difficult ≤ 20 %).
- **Calibration scan, always the full range:** f_eff 250–600 in 11 log steps × kappa 0.8–3.5 in 8 log steps (F5, shipped OFF: `K_GRID_BIKE = K_GRID`; switched on, a bike scans one more kappa step below, 0.65, if its HMM arrays fit the cap, `K_GRID_BIKE_ON`) (cell = 30·kappa m, one nominal step = one cell, + ln kappa per transition, as `rsm/hmm_cal`). The vehicle guess never narrows it. After the coarse scan the decode uses a local refinement around the peak (5 kappa factors 0.87–1.15 × 3 f_eff factors 0.92–1.09, +15 runs); the verdict statistic uses the coarse scan only, for real run and decoys alike.
- **Memory pre-check** (step 3, before any grid): cells × steps × 4 bytes at kappa 0.8 (backpointers 2 B + stored forward scores 2 B). Above 4 GB the step fails with exit code 3 and the log error `HMM arrays would need X GB ... use a smaller area`. A decoy box above the cap is dropped with a warning.
- **Vehicle** (soft prior, only road classes and default offset): votes for a motorised vehicle: heading noise ≥ 3× bike level, far-feature fallback share ≥ 15 %, lean p95 ≥ 15°, nominal speed p90 × 1.4 > 18 m/s; 2 votes (or the speed vote) → `motorcycle`, else `bike`. `auto` never answers `car` (no car among the development videos; car and motorcycle share classes and offset anyway). After step 4, with `auto`, a distance scale kappa ≥ 1.5 (≤ 1.3) switches the offset default to motorcycle (bike); a mismatch with the road classes is logged. PROVISIONAL: 3 bikes + 1 motorcycle.
- **Decoys: 19 = 3 foreign + 12 shuffle + 1 mirror + 3 foreign+shuffle**, all from the same extract, no network:
  - *foreign box rule:* boxes of the same size in km as the bbox, inside the extract; candidate centres on a lattice of half a box; at least half a box size away from the bbox; road length (same classes) within 0.7–1.4× of the bbox (widened once to 0.5–2×); the three closest in ln(density ratio) that do not overlap, ties south-west first. Fewer than three: the missing ones become extra shuffles (total stays 19).
  - *shuffle:* the heading increments cut into blocks of 200–500 m, permuted (seeds 100…); *mirror:* heading negated; *foreign+shuffle:* a shuffled series on a foreign box (seeds 150…).
- **Verdict without decoys (default).** From signals that need no decoys; PROVISIONAL thresholds from the four development runs. The verdict is labelled `verdict_basis: "without decoy check"` in the result event, `project.json`, `route_points.json` and the GPX metadata (`rsm:verdict_basis`).
  - `confident` only if all hold: calibration peak interior on both axes and ≥ 3 nats/km above the surface median; mean posterior ≥ 0.9 and ≤ 5 % of the time below 0.5; usable motion ≥ 85 %; heading noise < 8× bike level.
  - `no_route` if any holds: peak at the edge of the scan and < 1 nat/km above the median (this is how Amalfi with the vms yaw looked: the scan rose monotonically to the lowest f_eff); mean posterior < 0.5; usable motion < 50 %.
  - otherwise `uncertain` (the `reasons` list in `project.json` / the result summary says which condition failed).
  - Weakness, stated plainly: without decoys nothing tests the *identity* of the road against other plausible roads. A confident verdict here means a clean calibration and a decisive posterior, not a beaten decoy. The dev evidence is positive-only (the three bikes and Amalfi with far yaw are `confident`; Rousset's partial failure would be `uncertain` by its posterior share).
- **Verdict with decoys** (`--decoys N`; statistic: best-path log-likelihood per km, maximised over the same grid; PROVISIONAL thresholds): `confident` = rank 1 of 20 and margin over the best decoy ≥ 5 nats/km; `uncertain` = rank 1 with a smaller margin; `no_route` = rank > 1. Dev evidence: margins 13.1 / 14.5 / 2.5 (Rousset, last 940 s wrong) for the bikes, 12.2 for Amalfi with far yaw, −0.46 for Amalfi with vms yaw (rank 3). The GPX is written for every verdict; the app decides whether to show it.
- **Driving line:** the decoded OSM centre line shifted by `--offset-m` (default bike 1.5 m, motorcycle/car 1.6 m, one-way edges 0 m with an 8 m smoothed ramp) to the right in right-hand traffic, to the left in left-hand traffic (offline polygons for UK, IE, IM, Channel Is., JP, AU, NZ, ZA, IN/NP/BT/BD, LK, PK, CY, MT, HK, TH, MY/SG, KE/TZ/UG; partial, override with `--traffic-side`). The tangent angle is smoothed (Gaussian 4 m), the offset is clipped to 0.6 × the local radius on the inner side of a bend and smoothed again: no loops in hairpins (tests on Rousset and Amalfi hairpins, `tests/test_pipeline.py`).

## Progress protocol (stdout, one JSON object per line)

```json
{"type":"step","id":"route_search","index":4,"of":7,"state":"running","pct":63.2,"eta_s":240}
{"type":"step","id":"motion","index":1,"of":7,"state":"done","pct":100.0}
{"type":"step","id":"map","index":3,"of":7,"state":"skipped","pct":100.0}
{"type":"step","id":"map","index":3,"of":7,"state":"failed"}
{"type":"status","signal":"motion_coverage","level":"good","value":0.997,"message":"100 % of the video time has usable motion (1 segments)"}
{"type":"status","signal":"decoy_margin","level":"good","value":12.2,"message":"real route ranks 1 of 20, margin 12.2 nats/km over the best decoy (foreign:f1); verdict confident"}
{"type":"log","level":"warn","message":"area check: ratio 2.20 (good <= 1.5, problem > 3.0)"}
{"type":"result","verdict":"confident","verdict_basis":"without decoy check","gpx":"DIR/route.gpx","project":"DIR/project.json","route_points":"DIR/route_points.json","summary":{"decoys":0,"reasons":[],"signals":{"peak_interior":true,"conf_mean":0.989},"verdict_basis":"without decoy check","vehicle":"bike","offset_m":1.5,"traffic_side":"right","f_eff":426.1,"kappa":1.12,"confidence_mean":0.99,"route_km":21.9,"step_seconds":{"motion":950.0},"step_peak_gb":{"motion":0.4}}}
```

- `step.pct` is real (see the table); `eta_s` is elapsed × (100 − pct) / pct, present from 2 %; events are sent about once a second per step. `state` is `running|done|failed|skipped`. A step reused from an earlier run (`--resume`) is `skipped` with `"reused": true`.
- `status.signal` ∈ `motion_coverage` (value = usable share; good ≥ 0.85, difficult ≥ 0.50), `rotation_quality` (value = heading noise / bike level 0.0032; good < 3, difficult < 8), `calibration_peak` (value = best minus surface median, nats/km; good if interior on both axes and ≥ 3, problem if at the edge and < 1), `decoy_margin` (value = margin nats/km; only when decoys ran), `area_size`. `level` ∈ `good|difficult|problem`. All thresholds PROVISIONAL (APP_SPEC section 5). A signal may be sent twice (`area_size`: after step 1 and after step 4); on `--resume` the stored statuses of skipped steps are sent again.
- `log.level` ∈ `info|warn|error`. Every failure ends with an `error` log line and a non-zero exit. Worker diagnostics (stderr, tracebacks, memguard peak) go to `DIR/logs/<step>.err.log`, never to stdout.
- The last line of a successful run is `result`; `retime` prints one `result` line with `gpx`, `start_time`, `points`.
- vms progress: the vendored `vmsx.motion.analyse` takes an opt-in `on_progress(done, total, phase)` callback (default `None`: unchanged behaviour and console output), called at most once a second. So the percent is real and no CSV polling is needed. (The original `../video-motion-speed` is untouched.)

## Exit codes

| code | meaning |
|---|---|
| 0 | finished (any verdict) |
| 1 | internal error (traceback in `logs/`) |
| 2 | bad arguments or missing files (video, pbf, bbox, retime on an unfinished run) |
| 3 | resource: memory pre-check above 4 GB, memguard kill (12 GB / 25 % free), or too little free memory at start |
| 4 | data problem: bbox not inside the extract, no roads in the area, `FileNotFoundError`/`RuntimeError` in a step |
| 130 | cancelled (SIGTERM/SIGINT): the running step is stopped, `--resume` continues |

## Files written (only under `--out` and `RSM_DATA_DIR`)

```
DIR/route.gpx                one point per video second, <time> = start + t, lat/lon on the driving line, no <ele>
DIR/route_points.json        {"meta","verdict","driving_line","points":[{t,lat,lon,heading,confidence,in_gap,extrapolated,sd_m,arc_m,offset_m,line_source,[offset_sd_m]}]}  (rsm.bench.verify_map input)
DIR/project.json             all parameters, effective vehicle / side / offset, code hash, per-step summaries, plausibility result
DIR/project.params.json      the arguments of the run
DIR/steps/<id>.done.json     checkpoint: input hash, seconds, peak RSS, summary, statuses
DIR/{motion,rotation,map,route_search,[plausibility],refine}/   step outputs (motion.csv, tracks.pkl, graphs, route.pkl, decoys.pkl, result.npz, ...)
DIR/logs/<id>.err.log        stderr of the worker incl. the memguard peak line
RSM_DATA_DIR (default DIR/_cache)   pbf density map and extracted road graphs, keyed by pbf size/mtime + box + classes
```

GPX per point: `<extensions><rsm:confidence>` (forward-backward posterior of the decoded edge, 0 outside the decoded span), `<rsm:in_gap>` (inside a vms gap, distance estimated), `<rsm:extrapolated>` (before the first or after the last decoded step: position clamped to the route end). Metadata: `rsm:verdict`, `driving_line: approximation` with the offset rule, copyright/attribution "(c) OpenStreetMap contributors, ODbL". Seconds before the first decoded step and after the last are written with `extrapolated=1`.

## Resume

A step is skipped when `steps/<id>.done.json` exists and its input hash (video size/mtime, bbox, pbf size/mtime, vehicle option, frozen constants, and the hash of the previous step) is unchanged. `--start-time` is not part of any hash. `--decoys` changes only steps 5 and 7. An interrupted `plausibility` keeps `decoys.pkl` and continues with the next decoy; the other steps restart from their beginning. `--offset-m`, `--traffic-side` change only step 7.

## Resource behaviour

Peak group RSS per step is in `project.json` (`steps.<id>.peak_gb`) and the result summary. At most 4 worker processes (`fork` pools in steps 1, 2, 4, 5; step 1 takes `resources.policy()["workers"]`, which `RSM_MAX_WORKERS` can lower). Free system memory below 30 % at start aborts with exit 3. Nothing runs after the sidecar exits: memguard and the worker are killed when their parent disappears.

## Parallel motion (step 1, 2026-11-16; `vmsx.motion.analyse_parallel`, `MOTION_PARALLEL` in config.py)

- The horizon calibration runs its 16 stretches side by side, then the frame pairs are cut into chunks of `CHUNK_S` = 120 s, each decoded by its own `ffmpeg -ss` in a pool of `resources.policy()` workers (at most 4) with one OpenCV thread each. `motion.csv` is **byte-identical** to the sequential `analyse`; the motion hash is unchanged, so old projects resume.
- How it stays identical: the first chunk reads the video exactly like `analyse` (no seek). Every later chunk first decodes `WARM_FRAMES` = 32 frames before its first pair, so the destatic running mean (tau 2 frames) has forgotten its start, and the SHA-1 of those 33 frames must equal the last 33 frames of the chunk before, which must end on its planned frame. Rows go to `motion.csv.part` in order and replace `motion.csv` only when every seam matched.
- Fallback to the sequential `analyse` (same calibration, logged as a warning, `motion.json` `parallel.fallback` gives the reason): packets off the constant-rate grid (`decode.timing` `max_dev` >= 0.5 frame), packets flagged discard, a stream start other than 0, a video shorter than two chunks, or a seam that does not match.
- `motion.json` gains `parallel` = `{workers, chunks, chunk_s, warm_frames}` (or `{workers: 1, fallback}`). `MOTION_PARALLEL = False` restores the old path.
- Measured (M3 Pro, idle): Col de la Cayolle, 98 min 1080p50 AV1, whole motion pass 1429 s sequential (app run) against 640 s with 4 workers (2.2x, 49 chunks, csv identical); Roanne 300 s and Verdon 240 s clips 2.1-2.7x, identical. The CPU is the limit (Python plus ffmpeg per worker); software decoding does not scale (ffmpeg is already multithreaded). Another heavy job beside it removes the gain (a first Cayolle run under load: 1499 s).
- A seam that does not match sets a shared stop flag: running chunks return within 250 frames, the pool is closed and joined normally. `Pool.terminate()` mid-run is avoided: it can fork a replacement worker during the shutdown, which then deadlocks. Workers run with one OpenCV thread (a forked child cannot use the thread pool of a parent that already ran OpenCV).

## Packaging notes

- **One environment.** `rsm.pipeline` runs from a single Python 3.14 environment; vms is **vendored** as `rsm/pipeline/vmsx/` (frozen copy of `video-motion-speed/vms/{motion,decode}.py`; changes: ffmpeg/ffprobe lookup via the environment, `on_progress` callback, `probe()` falls back to the container duration because mkv files carry none in the stream). The far-feature tracking uses `cv2` from the same environment. Worker subprocesses are the same interpreter: `[sys.executable, "-m", "rsm.pipeline", ...]`, or `[sys.executable, ...]` when `sys.frozen` (PyInstaller); the internal commands `_step` and `_memguard` are subcommands of the one executable.
- **Runtime dependencies** (`requirements-pipeline.txt`, pinned): numpy, scipy, opencv-python-headless, osmium (pyosmium; it pulls `requests`), shapely, pyproj. Not used at runtime: osmnx, networkx, pandas, geopandas, matplotlib, scikit-image, gpxpy, dtaidistance. The road graph is built directly from the pbf (`rsm/pipeline/osm.py`, same graph as osmnx with `simplify_graph(edge_attrs_differ=['osmid'])`). Research modules that would create directories in the repository at import (`rsm.hmm.exp`, `rsm.refine.load`, `rsm.track2.*`, `rsm.quanta.*`, `rsm.nogps.*`, `rsm.plaus.*`) are not imported; the few functions needed are frozen copies in `steps_c.py`, `steps_b.py`, `tracks.py`. `tests/test_pipeline.py::test_lean_environment_imports_and_writes_nothing` imports the package in a fresh venv with only these requirements, from a read-only copy of the sources (set `RSM_LEAN_PYTHON`).
- **ffmpeg / ffprobe:** `RSM_FFMPEG` (default `ffmpeg` on PATH); `RSM_FFPROBE` (default: `ffprobe` next to `RSM_FFMPEG` if that is a path, else on PATH). Only decoding is used (`-hwaccel videotoolbox` when available, `RSM_HWACCEL=0` forces software; the filters are `select`, `scale`, `format`, `framestep`). The decode-only LGPL build needs the `rawvideo` muxer, the `scale`/`select`/`format`/`framestep` filters and the decoders of the supported videos.
- **Writes:** only `--out` and `RSM_DATA_DIR` (`DIR/_cache` when unset; nothing in the source tree or the home directory). Python bytecode is the only other write and can be disabled with `PYTHONDONTWRITEBYTECODE=1`.
- The pbf must be an extract that contains the bbox; the header box is checked (exit 4 otherwise). pbf passes take 10–20 s per 500 MB; graphs are cached per (pbf, box, classes).

## Local pass (refine step, from code hash ce932147653262c8)

The refine step first decodes the search route again in a corridor of `LOCAL_BUF_M` (300 m) around it. The corridor contains all drivable road classes: the vehicle's search classes plus `LOCAL_EXTRA` (residential, living_street, road, unclassified). The steps are `LOCAL_D0` (15 m) nominal; f_eff and kappa are taken from the search.

The pbf is read once per route box and cached as `graph_local_<key>.npz` in the data dir.

If no route fits the corridor, the search route is kept and the `local_pass` status is "difficult". Otherwise the status is "good", with value = the share of the route moved by more than 30 m.

`refine/summary.json` has `local` (corridor, steps, changed share) and `local_used`. `route_search/route.pkl` stays the search result, so the verdict is unchanged. The positions and the confidence come from the local pass.

There are no new CLI options. The refine checkpoint hash includes the LOCAL_* config and the pbf.

## Standstills and dense heading alignment (refine step, from code hash f109940ba15f1ee2)

**Measured gaps.** A gap between two vms tracks whose pairs are at least `GAP_MEASURED_SHARE` (70 %) well fitted gets its measured vms distance. Without it, the gap is filled with the mean speed. This is used in the local pass.

**Dense heading alignment** (`align.py`). After the local pass, the video heading samples (4 m nominal) are aligned to the fixed path by a monotone Viterbi on a 2 m grid. The path heading is smoothed across junction nodes. Positions where the path turns at least `ALIGN_TURN_DEG` within ±`ALIGN_TURN_HALF_M` become smoother measurements with sd `ALIGN_MEAS_SD_M`.

If the alignment leaves the HMM route by more than `ALIGN_MAX_DEV_M`, it is rejected. The rejection is logged and the previous measurements are used.

`refine/summary.json` has `align` (samples, gaps, deviation from the HMM route, used).

## Sure standstill (route_search / every route-side step / refine / gpx / export, 2026-11-16; `rsm.pipeline.standstill`, `STILL_*` in config.py)

The camera stands while other vehicles pass close by: vms reads their flow as ego-motion (Amalfi 4881–4884 s: 1–2 m/s and about −22° of phantom turning). Research, labels and numbers: `work/standstill/` (README, results.md; P 0.94 / R 0.98 on 306 labelled 0.5-s windows of four videos, PROVISIONAL: no held-out video yet).

- **Detection** (start of route_search, about 20–45 s per video hour): candidate 0.5-s windows = vms rel_speed below `STILL_GATE_REL` × the video median (0 included) and far-only heading change below `STILL_GATE_FAR`. Only those are decoded (360 rows). Test per window: whole-frame Lucas-Kanade over `STILL_BASE_S`, a global similarity by RANSAC ("the camera only sways / turns"), an 8×6 grid; a cell is static when ≥ 60 % of its tracks fit within 0.35 px. **Sure** = static share ≥ `STILL_ALL` over the frame and ≥ `STILL_UP` above the vms horizon. Long candidate runs: every window within `STILL_EDGE_S` of the ends, one every `STILL_SAMPLE_S` inside (a window between two sure samples counts as sure; where two neighbouring samples disagree, every window between them is tested, up to 3 rounds). Spans shorter than `STILL_MIN_S` are dropped. Result: `route_search/standstill.json` (spans, tested windows); status `standstill` (good, value = seconds held).
- **Three kinds of gap now:** a *sure standstill* (measured, held), a *measurement gap* (odometry failure, cut, darkness: estimated, free) and the former *measured gap* (A6, vms ≈ 0 with good fits). A sure standstill wins over a failure estimate.
- **Search and every route-side step** (`odofail.build`, so map info, route_search, plausibility, local pass and refine alike): the tracks are split at the spans (no phantom distance or heading), and the gap gets its MEASURED distance = vms distance of the pairs outside the span, zero inside, with far-only heading. The main search now measures such gaps too (before, a stop was filled with the speed before and after).
- **Fusion** (`steps_c.hold_still`): the span ends are nodes; between them the map and gap distance is 0 (no process noise: the position is held) and no posterior or alignment measurement inside counts. The rest of the route is unchanged.
- **Output:** `refine/result.npz` has `in_still` and `still_t0/t1/s0/s1/sd/conf`; `route_points.json`: every point has `motion_state` (`driving`, `standstill`, `gap`; `in_gap` is false in a standstill), and `standstills` lists `t0`, `t1` (exact video seconds), position, arc. `route.gpx` carries one extra point at each start and end (`rsm:edge` standstill_start / standstill_end, `rsm:state`), with millisecond time (`…T00:01:21.500Z`); whole seconds keep the old format. `retime` keeps them.
- **Incyclist export:** the edges join the exported seconds; speed 0 inside, and the speed guard spreads no capped distance into a standstill. The thinning keeps the first and last point of a standstill as before, now at the exact edges. Whether Incyclist reads sub-second `<time>` is not checked in Incyclist itself.
- Off switch: `STILL_ON = False` (re-freeze): no detection, nothing read, results as before.


## Passing traffic while moving (all route-side steps, 2026-11-17; `rsm.odometry.gating`, DECISIONS A17)

A vehicle passing close by (overtaking from behind, oncoming) takes over the vms road fit: the trimming threshold scales with the median residual, so nothing is trimmed and the speed is a blend of road and vehicle (overtaking reads slow, oncoming fast; Amalfi median -16 % in the final GPX at an overtake, up to -35 %). Such pairs have a fit rms of 1-3 px against about 0.2 px on plain road.

- `GateParams.max_rms_px` 2.0 -> 0.8: those pairs are `high_rms` (unusable).
- A run of unusable pairs without a cut that lasts up to `traffic_bridge_s` (4 s), is at least `traffic_share` (30 %) high-rms and has usable speed >= `traffic_min_rel` (0.3) x the video median in the `traffic_side_s` (1 s) before and after is **bridged** (speed and heading interpolated) instead of splitting the track. A stop with traffic stays with the sure standstill (above) and the measured gaps.
- The odometry-failure share (`odofail.quality`) still counts rms-only rejections up to `ODO_FAIL_RMS_PX` (2.0) as usable, so failure spans are unchanged.
- Checkpoints: motion is reused; rotation (tracks) and every later step change.
- **In the fit itself** (DECISIONS A18, `vmsx.motion` `ALT_*`): a pair whose plain fit has rms above `ALT_TRIGGER` (0.6 px) gets up to `ALT_KEEP` candidate road fits with a fixed inlier distance, written to the new column `alts` (`s c yaw pitch roll inliers rms`, `;`-separated, the plain fit first). After all pairs `pick_alternatives` puts the candidate closest to the clean road speed in the `ALT_REF_S` (1.5 s) before and after in place of the fit (within `ALT_TOL`, 30 %); column `pick`: empty = no candidates, 0 = plain fit kept, k = candidate k, -1 = none fits (the row stays; the gate above rejects and bridges it). `motion.json` `traffic` counts them. Candidates are seeded by the frame number, so the parallel motion step stays byte-identical. Motion hash token `motion2`: every project computes motion again. `inspect-frame` compares only the columns the pick leaves alone for a replaced row.

## Incyclist export (`export`, no checkpoint; video2gpx `docs/FEATURE_incyclist_export.md`)

```
python -m rsm.pipeline export --out DIR --dest FILE.gpx --summary FILE.json [--dem-dir DIR] [--fps 50] [--trim auto|off] [--start-time ISO] [--title T] [--link URL] [--app-version V]
```

Reads a finished run (`refine/result.npz`, `project.json`; `map/graph_real.npz` for old results) and writes the GPX for Incyclist plus a JSON summary. It is cheap (about 1 s), writes only `--dest` and `--summary`, and has no step of its own (repeating it is the way to change it). Exit 2 without a finished run, 4 on a refused DEM file. Progress: `{"type":"step","id":"export","index":1,"of":1,"state":"running","pct":..,"phase":..}`, then one `{"type":"result","gpx","summary_file","summary":{...}}`.

- **Trim** (`--trim auto`, default): only the decoded span is written (the seconds with `extrapolated=true` at the start and the end are dropped). The first written second `t_first` gives the Incyclist start frame `round(t_first × fps) + 1` (needs `--fps`, the exact `r_frame_rate`; null without it). The video is not cut.
- **Times:** without `--start-time` the first written point is `2000-01-01T00:00:00Z` (Incyclist only uses the time relative to the first point); with it, `start + t` as in `run`.
- **Speed-spike guard:** a step faster than the vehicle's maximum (bike 25 m/s, motorcycle and car 50 m/s) is capped and its excess spread over the neighbouring seconds (growing window, up to their headroom); start, end and length stay. Positions are recomputed on the same driving line as step 7.
- **Standstills:** at most one point per 0.5 m of progress, but the first and the last second of a standstill are both kept (at least 0.1 m apart), so the frames of a stop map to almost no distance. The GPX is otherwise one point per second.
- **Elevation** (`rsm/pipeline/dem.py`, numpy + zlib only): Copernicus DEM GLO-30 tiles `Copernicus_DSM_COG_10_<N43_00>_<E007_00>_DEM.tif` in `--dem-dir` (or `RSM_DEM_DIR`); a `<name>.none` file marks a tile that does not exist (sea, sampled as 0 m). Minimal TIFF reader: tiled, DEFLATE or none, float32, predictor 1 or 3, GeoTIFF scale / tie point / PixelIsArea or PixelIsPoint; anything else raises `UnsupportedTiff` (never guessed). Bilinear sampling every 5 m along the driving line, then:
  - tunnel and bridge runs (`tunnel` / `bridge` of `result.npz`, widened by 15 m) are replaced by the straight line between the portals / abutments;
  - **noise-adaptive smoothing** (2026-11-13). The local DEM noise is the RMS (Gaussian window 300 m) of the samples around a robust local-linear fit (sigma 60 m). Where it is below 3 m (clean DEM): a running **lower** quantile (25 % over 200 m) and a Gaussian (sigma 60 m), because the DEM is a surface model and trees and buildings only ever raise it (the plan's median 25 m + Gaussian 20 m overestimated the ascent on five Van Gestel GPS tracks in the Drôme by 5–40 %, x3 on Roanne; the lower quantile gives 1–16 %). Where it is above 10 m (a road cut into a cliff: the 30 m pixels mix the rock above with the sea or a gorge below, so the DEM errs down as often as up, ±30 m within 100 m): the running **median** over 200 m and a **robust local-linear fit** (Gaussian kernel sigma 150 m, 4 bisquare passes, cut-off max(5 m, 6 × median |residual|)). Linear blend of quantile and filter between 3 and 10 m. The lower quantile alone followed the gorges on the Amalfi coast (ascent +35 % against Strava's profile of the same route);
  - grade clamp ±18 % by alternating projections (each too steep 5 m step moves both ends towards each other by half the excess, until none is left): keeps the local mean, so it does not drift. The earlier clip-and-re-integrate left a 10–13 m step behind a clamped gorge for the rest of the Amalfi route. Steep-edge tags (±25 %) are not read yet;
  - ascent / descent with 3 m hysteresis.
  Missing tiles: the GPX is written without `<ele>` and the summary says which tiles are missing.
  **Since code hash 14613ce583ab93c5 (P17)** the elevation goes through `export.corrected_elevation`, which uses every source cached under `--dem-dir/<source>/` (see "Elevation sources"). With none cached the result is exactly the profile above.
- **GPX:** `trkpt` with `<ele>` (0.1 m), `<time>`, `<extensions><gte:gps speed="km/h"/><rsm:conf>` (the Van Gestel `gte` namespace); metadata name, description (driving-line rule, "reconstructed from the video, no GPS", confidence summary), ODbL copyright, link, `creator="video2gpx <app> / rsm.pipeline <version> <hash>"`, `rsm:start_frame`, `rsm:elevation`.
- **Summary JSON:** points, thinned points, trimmed seconds (head, tail), `t_first`, `fps`, `start_frame`, `length_m`, `ascent_m`, `descent_m`, `elevation` (tiles, missing, tunnel / bridge metres and counts, interpolated metres, clamped metres, `noise_median_m`, `noisy_share` (share of the path with the noisy-DEM filter weight above 0.5), filter constants incl. `noise_lo_m`, `noise_hi_m`, `high_quantile`, `rloess_sigma_m`, `bridge_source`), speed guard, start / end / bbox (the app reverse-geocodes the start for the country), confidence mean and share below 0.5, verdict, vehicle, offset, side, pipeline hash.

## Calibration candidates (route_search, accuracy work 2026-11-12)

The scan surface can have a high corner maximum that is physically impossible (Madone without hints: f_eff 148 / kappa 6.6 needs 9 m/s2 lateral acceleration and 31 m/s at the 95th / 99th percentile). `calib.py` computes from `rotation/tracks.pkl` the speed and lateral acceleration a calibration implies (`a_lat = |yaw rate| x F_REF / f_eff x speed`, speed proportional to kappa). A cell is implausible if the 95th percentile of a_lat exceeds `CAL_ALAT_MAX` (5 m/s2) or the 99th percentile of the speed exceeds `CAL_VMAX` (45 m/s; `CAL_VMAX_BIKE` for a bike, explicit or estimated: F2 of 2026-11-13, shipped OFF = 45 m/s, tested value `CAL_VMAX_BIKE_ON` 20 m/s). The grid extension follows the best plausible cell and does not scan rows / columns without a plausible cell. The first candidate is the best plausible cell; only if its decode is not confident, up to `CAL_N_CAND` (3) plausible local maxima are refined and decoded, and the best by (verdict, plausible, interior peak, score) is used. A video with one plausible maximum behaves exactly as before.

`route.pkl` gets `candidates` (per candidate: f_eff, kappa, score per km, mean posterior, verdict, interior, plausible, a_lat p95, v p99, chosen) and `calibration` (cells, plausible cells, the global maximum and whether it is plausible, the motion statistics, the limits). New status `calibration_choice` (only when the global maximum was implausible or more than one candidate was decoded; value = number of candidates decoded; `difficult` if the chosen one is not confident or a second confident candidate gives a different route). New soft verdict reasons: "two calibration candidates of similar quality give different routes", "the calibration needs more speed or lateral acceleration than a road vehicle has".

## Cuts (motion / rotation / refine / gpx, F4 2026-11-13; `rsm.pipeline.cuts`, `CUT_*` in config.py)

An edited video (cuts into other places, inserted title shots or close-ups) is not one continuous ride. A scene cut is now a **jump**, not riding.

- **Detection, no extra decode.** From the frame pairs the vms pass already analysed (motion.csv `diff`, `inliers`) and the far-feature windows of the rotation pass: a pair is a cut when its frame difference is a spike (above 4 x its 61-pair running median and above 25, the gating constants) **and an impulse** (above `CUT_IMPULSE` = 2 x the largest of the +-3 pairs around it: a cut changes one pair, a bump / flash / pan several) **and** a model fails there: the road-flow fit (fewer than 20 inliers or < `CUT_INL_SHARE` = 25 % of the inliers around) or the far-feature rotation fit of the window across the pair (no band fits or < 25 % of the inliers around). **Strong-impulse gate (2026-11-16, user request; Cayolle HDR intro cuts 0:41.67 / 0:49.25, Clue du Pérouré 0:50.33):** a pair under the spike gate above is a candidate too when the road-flow fit **collapses at that one pair**: fewer than 20 inliers there, a median of at least `CUT_STRONG_AROUND` = 100 over the +-25 pairs around it, and every pair of the +-3 around it at `CUT_STRONG_NB_SHARE` = 20 % of that median (a flash or bump breaks several pairs); plus an impulse of `CUT_STRONG_IMPULSE` = 2.3, a difference of `CUT_STRONG_FACTOR` = 2.3 x the running median and `CUT_STRONG_MIN_DIFF` = 15. Pairs within `CUT_MERGE_S` = 0.5 s are one cut. `motion/cuts.json` = candidates (diff + road-flow cue), `rotation/cuts.json` = the decision: `cuts`, `cut_times`, `intro_end`, `inserted`, `dropped_tracks`, the candidates with both cues, the parameters.
- **Same-scene veto (2026-11-16, user request; `CUT_SAME_*`).** The only extra decode: for every cut found above, the grey frames within +-`CUT_SAME_WIN_S` = 0.12 s (270 rows) are decoded, the jump pair is the largest frame difference there, and the frame before it is compared with the frame after it: both brightness-normalised, corners tracked (LK, forward-backward), one similarity fitted by RANSAC. If at least `CUT_SAME_SHARE` = 20 % of the corners fit, the scene is the same (a sun flash or an exposure jump): **no cut**. Such candidates are kept in `rotation/cuts.json` as `rejected` (each cut and rejected entry has `same`: {t_before, t_after, corners, inliers, share}); log line "scene cut candidate at m:ss rejected". Measured: Gotthard HDR sun flashes 3:12 / 3:14 share 0.48 / 0.37; 19 real cuts (Bavaria 13, Amalfi 4, Gotthard and Madone intro) <= 0.07. Undecodable frames keep the cut. The rotation hash gets `["same1", CUT_SAME_SHARE, CUT_SAME_WIN_S, CUT_SAME_H]` while the veto is on (old projects recompute the rotation step). Tests: `tests/test_cuts.py`, including the real-video checks Gotthard 3:00-3:20 (no cut) and 0:10-0:30 (the intro cut stays), marked `realdata`.
- **Handling.** The tracks are split at every cut (as before, gating); a track after a cut carries `cut_before`. A piece between two cuts shorter than `CUT_MIN_PIECE_S` = 20 s is an inserted shot: dropped and reported. In the HMM steps a cut gap is `ceil(CUT_JUMP_M / 2 d0)` (25 at 30 m) sub-steps with ~0 nominal distance and a distance prior: each sub-step advances Normal(0, sd / sqrt(n)), forward along the graph, so the walk through the jump is half-normal with sd. **Default (maintainer decision 2026-11-13): a FLAT jump**, `CUT_PRIOR_SD_M` = 1e5 m: every start up to about 1.5 km forward costs the same. Option / way back: `CUT_PRIOR_SD_M = CUT_PRIOR_SD_SOFT_M` (400 m, a soft stay prior: a start d m further costs about d^2 / 2 sd^2 nats; it came from an edit whose origin is unexplained, docs/DECISIONS.md A13). Bavaria clip (bike paths on, hint corridor): flat 84 % within 30 m / median 3 m, soft 21 % / 188 m; Amalfi identical. `CUT_PRIOR_SD_M` is part of the `route_search` input hash. Heading increments never cross a cut. The forward-backward posterior uses the same prior. The smoother holds the position from the last step before a cut and lets it jump at the first step after it (sd `CUT_FUSE_SD_M`, measurements inside the jump dropped); the dense heading alignment runs per piece between cuts. Why not independent HMM runs per piece: the scan, decoys and verdict would have to be run and combined per piece; the jump keeps one route, one calibration and one score.
- **Start rule (maintainer).** With cuts in the first `CUT_INTRO_S` = 120 s the route starts after the LAST of them: its tracks are dropped, the GPX and route_points.json start at the first second after that cut (video time stays the time base), status `intro_skipped` ("intro up to m:ss skipped"; app: "Intro bis m:ss übersprungen"). Without cuts in the first 2 minutes nothing changes. If nothing were left after the intro, the rule is not applied.
- **Output.** route.gpx gets `<rsm:cuts n=".." [intro_skipped_s=".."]>t1 t2 ..</rsm:cuts>` in the metadata and one `<trkseg>` per piece between cuts (a new segment at the first point after each jump); route_points.json gets `cuts: {times, intro_end, breaks}`; points from the last step before a cut to the first second after it have `in_gap` = 1; refine/summary.json `cut_spans`. Status `scene_cuts` (level difficult, value = number of cuts; app: "Schnitte").
- **Unchanged without cuts**: no `cut_before` in the tracks, steps = `rsm.hmm.seq.make_steps`, no cut spans, one trkseg, no new keys (tracks.pkl, vehicle.json, steps, route.gpx byte-identical; only `motion/cuts.json` and `rotation/cuts.json` are new files). `CUT_ON = False` switches all of it off.
- Checkpoints: the motion step's results are unchanged (cuts.json is extra); the rotation step's tracks change for a video with cuts: its input-hash token in cli.py is bumped (`rotation1` -> `rotation2`, integrator 2026-11-13) so old runs recompute tracks.pkl (and every later step); the `CUT_*` constants are in `frozen.json`; a resumed old motion step without cuts.json is handled (candidates are recomputed from motion.csv).


## Elevation sources (P17, code hash 14613ce583ab93c5; docs/ELEVATION_STRATEGY.md)

- **Directory layout.** `--dem-dir` holds the Copernicus GLO-30 tiles at the top level (unchanged; the app downloads them). Extra sources are in `--dem-dir/<source>/`:
  - `<block>.npz`: float32 `z` (NaN = nodata), `x00`, `y00` (centre of pixel 0, 0), `res`, `epsg`;
  - for 1° sources, the provider's GeoTIFF `<tile>.tif`;
  - `<block>.none` = the provider has no data there. Server errors leave no marker; the block is retried.
- **Registry** (`rsm/pipeline/demsrc.py`, `SOURCES`):
  - `cop_flm` (mask), `nasadem` (fill);
  - `fr_rgealti`, `it_tinitaly`, `it_bz_dtm`, `ch_swissalti3d`, `at_als_dtm`, `de_by_dgm1`, `de_he_dgm1`, `de_nw_dgm1` (terrain models);
  - `aw3d30` (unverified terms, disabled).

  Enabled are all `verified` sources with `enabled=True`. `RSM_DEM_SOURCES=a,b` or `--sources` narrows the set (for tests and comparisons).
- **`dem-plan`** reads the run (`refine/result.npz`, `project.json`), samples the whole decoded path on the driving line every 5 m, and lists per source the blocks within 60 m of it. A fill source is listed only where the cached fill mask shows void-filled Copernicus pixels on the route; while the mask is not cached it is listed as `conditional`. No network.
  `{"type":"result","sources":{name:{title,kind,region,blocks,missing,conditional,licence,attribution,status}},"missing_blocks":n,"missing_bytes":estimate,"exact":false}`.
- **`dem-fetch`** downloads the missing blocks, sequentially, with 0.2 s between requests: the mask first, then a fresh plan for the rest. Events: `{"type":"progress","index","of","bytes","source","block"}`, then `{"type":"result","ok","fetched","of","bytes","errors":{source:{count,last}}}`. A source that fails three times is skipped for the run. Exit 0 also with errors (they are in `errors`); exit 2 without a run or a DEM directory.
- **Estimator** (`dem.profile_multi`; constants `RS_*`, `RUG_*`, `DTM_BLEND_M`, `MULTI_SOURCE` in dem.py):
  - corridor samples of all sources (`collect_samples`);
  - where a terrain model has data, the robust penalised spline (`robust_road_height`);
  - elsewhere, Copernicus with FLM-filled pixels replaced by the aligned mean of the fill sources, then the P13 filter;
  - feathered over 100 m, then tunnels and bridges, then the grade clamp.
- **Summary and profile JSON, new fields.**
  - `elevation`: `strategy` (`p13`, `p13+fill`, `robust-multi`), `sources_used`, `source` (titles joined with " + "), `attribution` (all used sources, "; "-joined), `sources` ([{name, title, licence, attribution}]), `fill_share`, `dtm_share`, `ruggedness_mean`, `datum` (the measured datum mode per source vs Copernicus), `ell_mean_m`, `consensus_median`.
  - The GPX `rsm:elevation` is `copernicus-glo30` plus the used sources joined with `+`, for example `copernicus-glo30+fr_rgealti`.
  - The `profile` result adds `sources_used`.
- **`profile` and `elevation_diag.json`** (since the elevation stage, 15 Nov 2026; docs/FEATURE_elevation_stage.md). `profile` writes `FILE.json` (the profile) and, in the same directory, `elevation_diag.json` (what the profile was made of). `z` is exactly what it was before: the diagnostics only read the estimator's intermediate arrays (`dem.profile_multi(..., diag=)`, `dem.robust_road_height(..., diag=)`); a test compares `z` with and without them.
  - `FILE.json` stays compatible and gains `diag` (`"elevation_diag.json"`, absent where the estimator did not run), `pipeline_hash` (the frozen code hash it was made with; already there since P17) and `blocks` (`{source: n blocks of this route in the cache}`, from `dem-plan`; the app compares it with the cache to see whether a source block was added or removed). The app calls a profile **current** when `pipeline_hash` equals the app's code hash and `blocks` equals the plan of the cache now (Rust `profile_stale`, field `stale` of `profile_load`).
  - `elevation_diag.json`, `version` 2, compact JSON (about 0.8 MB per 62 km). Everything is on the profile's grid: index i is arc `s0 + i·ds` (`s0` 0, `ds` 5 m, `n` samples), numbers rounded to 0.1 m or 0.01, NaN as `null`.
    - `z_p13`: the profile without national or regional sources (Copernicus, fill, P13 filter), metres.
    - `rug`: terrain ruggedness 0–1. `filled`: Copernicus pixel void-filled (0/1). `gap`: tunnel or bridge, widened by the portal pad (0/1). `w_dtm`: blend weight of the robust estimator (0 = P13 only, 1 = robust only).
    - `sources`: `[{name, title, colour, z, w, sh}]`, `colour` the index of the source in the list. `z` is the sample at the road axis (offset 0), cross-slope corrected and datum-aligned like `_stack` does it. `w` is the plausibility the estimator gave it in the last pass, `1 / (1 + (residual / scale)²)` in 0–1 (0 where the sample is missing or in a gap; `null` for the whole source where the estimator did not run). `sh` is the share of the source in the final height at that station (its summed final weights over all columns divided by the total, blended with P13 by `w_dtm`; in P13 stretches Copernicus has 1).
    - `strategy_share` (`{robust, p13}`), `source_share` (`{name: mean sh}`), `max_grade_pct` (largest grade over 50 m), `ascent_m`, `descent_m`, `ascent_p13_m`, `descent_p13_m`, `pipeline_hash`.
- **`export` reuses the profile.** When `out/elevation_profile.json` is current (hash and blocks as above, and newer than `refine/result.npz`), the export does not compute the elevation again: the height of each GPX point is interpolated from the 5 m profile at the point's arc, so the GPX `ele` are the profile's values. The summary's `elevation` then carries `profile_reused: true` and the profile's `corrections`, `source`, `sources`, `attribution`. Otherwise it computes as before. (`export(use_profile=False)` forces that in code.)
- `dem-plan` also reports `missing_bytes` per source.


## Analysis viewer (`inspect-series`, `inspect-frame`; `rsm.pipeline.insight`, docs/FEATURE_analysis_insight.md Part A)

Both commands read a finished run (`refine/result.npz`, `motion/`, `rotation/`, `route_search/route.pkl`) and write nothing but the series file. No step changed; existing outputs are byte-identical.

- **`inspect-series --out DIR [--dest FILE] [--window-m 30]`** writes the series JSON (default `DIR/inspect/series.json`, compact) and prints `{"type":"result","series","n","stretches","seconds","bytes"}`. Fields: `version` (1), `pipeline_hash`, `result_mtime` (whole seconds of `refine/result.npz`; the app recomputes when either differs), `n`, `t0`, `dt` (1), then per second arrays (null = no value): `t`, `s` (arc, m), `speed_fused`, `speed_vms` (m/s), `yaw_vms`, `yaw_far`, `yaw`, `pitch`, `roll` (deg/s, left positive), `inliers`, `rms`, `usable`, `far_ok`, `far_inl`, `far_why` (0 ok, 1 few corners, 2 few inliers, 3 narrow, 4 fit not trusted), `kappa_video`, `kappa_map`, `kappa_diff` (1/km, left positive, over `window_m`), `conf`, `p_search`, `s_sd`, `in_gap`, `extrap`, `tunnel`, `cut`, `odofail`, `local` (0/1/2); `cells` (per 100 m: `dev`, `match`, turning), `odofail_spans`, `cuts`, `limits`, and `stretches`: `{t0, t1, s0, s1, dur, kind low|none, conf_min, conf_mean, causes: [{id, text, value, limit, unit}]}`. The causes and their limits are listed in the spec's "Implementation notes (Part A)". 1 to 4 s for 2 000 to 7 600 s of video.
- **`inspect-frame --out DIR --t S [--video FILE] [--what motion,rotation]`** prints one `{"type":"result", t, video, fps, frame_width, frame_height, motion, rotation, seconds}`. `motion`: the vms pair at T (`pair`, `horizon`, `roi`, `polygon`, `points` as `[x, y, dx, dy, inlier]` in px of the 360-row analysis frame, `fit`, the recomputed csv `row`, the `stored` row, `agree`, `diff`). `rotation`: the far-feature window (`window`, `ta`, `tb`, `band_ends`, `bands[]` with points, fit, stored fit and `agree`, `chosen` = the band the series uses, `yaw_deg_s`). A part that cannot be made has `{"error"}` instead. The frames are decoded with the run's own parameters (`motion.json`, `win_video_base.npz` meta); `agree` is true when the row and the fits equal what the steps stored (tested on a synthetic video; on Verdon, Gotthard 2486 s: 26 of 26 samples). Videos with irregular timestamps can disagree. About 0.8 s per call plus about 1 s of interpreter start.
