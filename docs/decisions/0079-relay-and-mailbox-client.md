# ADR 0079: Relay and Mailbox Client

Status: **proposed** on 2026-11-09, on the maintainer's request to cut the requests to intervals.icu further (the companion of [ADR 0078](0078-drafts-for-external-data-sources-and-request-budget.md)). The server side (a Cloudflare relay with a mailbox) is built in its own worktree; this ADR is the app side of its protocol (`web/PROTOCOL.md`). The number was moved up twice because 0076 and 0077 were taken.

## Context

Reading every 15 minutes to learn that nothing changed is the biggest remaining cost. intervals.icu can push webhooks, but only to a public URL, and the app has none. A small relay at `https://ridrs.app` receives the webhook, seals each event for the one device it belongs to (the relay cannot read it later) and keeps it in a mailbox until the app has fetched and acknowledged it. The same host serves the pages that bounce the OAuth redirect and links to the app (`ridrs://…`).

## Decision

1. **Where.** The mailbox client lives in `planner-intervals-icu` (`mailbox.ts`, `mailbox-crypto.ts`, `mailbox-events.ts`): it applies the events to the plugin's cache and state, and plugins cannot import each other. The base URL is the constant `RELAY_URL = 'https://ridrs.app'` with the override `mailboxConfig.baseUrl` for tests. Mailbox requests go through `net.http` but not through the intervals.icu gateway (they are not intervals.icu requests and do not count against its budget). The Tauri http plugin's scope allows only `/devices`, `/devices/*`, `/updates`, `/updates?*` and `/updates/*` of `https://ridrs.app`.
2. **Keys.** On the first connect the device makes an Ed25519 key pair (signs requests) and an X25519 key pair (opens events). The private keys and the `device_id` are in the secret store (`ridrs-mailbox.sign-private`, `ridrs-mailbox.enc-private`, `ridrs-mailbox.device-id`) and nowhere else: not in app files, state topics, logs or test output. The cursor and the last timestamp used are not secret and live in the app file `training/mailbox-state.json`.
3. **Registration** is `POST /devices` with the public keys and the token, once, over TLS, right after every successful sign-in. It is always a new device: the device of an earlier sign-in is deleted (`DELETE /devices/<id>`, best effort, signed with its own keys) and its keys are replaced, so a different athlete never inherits the old binding. The relay uses the token the relay uses the token to learn the athlete id and drops it. An account that was connected before this version is not registered at start: sending the token again needs the rider's sign-in (reconnect). Failure of the relay is silent.
4. **Pickup** at start (after the cache is shown) and after a connect: `GET /updates?since=<cursor>&limit=50`, repeated while `more`, then `POST /updates/ack`. Every request is signed over `METHOD \n pathAndQuery \n timestamp \n hex(sha256(body))`; the timestamp is `max(now, last + 1)` and is stored before the request is sent. The requests of one device run one after another. Only a 401 with the body `{"error":"unknown_device"}` means the relay does not know the device: then the keys are dropped and the next sign-in registers again. Any other 401 (clock skew, a timestamp out of order) keeps the keys: the request is tried once more with a fresh timestamp and then given up until the next pickup. A refused socket (401 or 4401) says nothing of why, so the app asks with a signed `GET /updates` and acts on that answer in the same way; a device that is still known reconnects with the backoff. If the relay cannot be reached nothing is shown and the app works as without it (ADR 0077). There is no app-wake-up event in the contracts, and none is added without a use case: the wake-up of a mobile app is covered by the socket's reconnect (P2.3, below) and by the next start.
5. **Events** are opened with `X25519(device_enc_priv, eph_pub)`, HKDF-SHA256 (salt `eph_pub || enc_pub`, info `ridrs-mailbox-v1`) and AES-256-GCM (`nonce(12) || ct || tag`, aad `device_id|type|timestamp`). A test vector (`tests/fixtures/mailbox/mailbox-v1.json`, copied from the server's `web/test-vectors/`) pins the format in a unit test. An event that does not open is dropped. The plaintext is checked with zod per type before use.
6. **Meaning.** `CALENDAR_UPDATED`: its `events` and `deleted_events` change the planned workouts with no request. `SPORT_SETTINGS_UPDATED`: the FTP of the payload is applied, else the athlete's settings are read again (one request). `WELLNESS_UPDATED`: the athlete is read again. `ACTIVITY_UPLOADED` and `ACTIVITY_ANALYZED`: the events resource is read again. `APP_SCOPE_CHANGED` and unknown types: ignored. Events of our own writes (an `oauth_client_id` equal to ours, or an `external_id` this device uploaded) are ignored. An event seen before (by id) changes nothing, and for each calendar event the newest mailbox timestamp wins. The 24-hour validity of the library and the one-hour validity of the athlete (ADR 0077) stay as the safety net of a full resync.
7. **Crypto library: `@noble/curves`, `@noble/hashes`, `@noble/ciphers` (MIT, pure JS, ESM, audited, pinned).** WebCrypto covers Ed25519 and X25519 only in newer engines (Safari 17, Chromium 133 or later); the Android WebView and the Windows WebView2 follow the installed Chromium and the Mac's WebKit the OS, so the support would differ by device and could not be tested headless. Pure JS is the same code on every platform and in the scenarios. The costs are a few hundred lines of dependency code in the bundle and no hardware keys; the keys are in the secret store either way. The licenses go into `NOTICE`.
8. **Sign-in redirect and deep links (P2.1).** `auth.browser-sign-in` gets `deepLink?: boolean` on the provider and `relayRedirectUri?` on the request. A provider that can receive `ridrs://` links says so, and the planner then uses the redirect URI `https://ridrs.app/intervals/oauth/callback`, which the relay bounces to `ridrs://oauth/intervals?code=…&state=…`; the state is checked as before. Otherwise (a provider without deep links, or `tauri dev` on the Mac, which does not register schemes) the loopback sign-in of ADR 0049 is used, unchanged. The Tauri provider uses the official `tauri-plugin-deep-link` (Apache-2.0 or MIT) and also handles a link that started the app. The choice is the provider's flag, so it is explicit and testable. A deep link is untrusted input: its shape is checked, anything unknown is ignored. `ridrs://activity/<external_id>` (`^[A-Za-z0-9._-]{1,128}$`) opens the debriefing of that session if it exists and is otherwise ignored.
9. **Socket (P2.3).** A fast path beside the mailbox: `wss://ridrs.app/updates/ws?device&ts&sig`, the signature over `GET \n /updates/ws \n ts \n sha256("")` in the query (a webview cannot set headers), same key and the same strictly rising timestamp. The transport is the new capability `net.websocket` (a port: `connect(url, listener)` with text messages), implemented in the native app by the official `tauri-plugin-websocket` (Rust, so the CSP's `connect-src` stays closed) in the plugin `net-websocket-tauri`, and simulated in the scenarios; the planner declares it as `optionalRequires`, so a host without it has no socket. The plugin has no URL scope, and the only caller is the mailbox. The socket opens first, then the app fetches `GET /updates` (repeated while `more`) and de-duplicates by cursor; pushed events go through the same open, validate, apply and idempotency path as fetched ones and are acknowledged over the socket (`{"t":"ack","upto":n}`). The client sends `ping` every 30 s. Code 4000 (replaced) does not reconnect; 401 before the upgrade or 4401 drops the registration; any other close reconnects after 1 s, 2 s, 4 s … up to 60 s with ±20 % jitter, starting over after a connection that held for a minute. The socket lives while the account is connected and the device registered; it closes on disconnect and when the page is hidden (`visibilitychange`, where there is a document) and opens again, with a catch-up, when it is shown. No timer polls intervals.icu.
10. **Disconnect** calls `DELETE /devices/<id>` best effort and drops the keys and the state.
11. **Sign-in confirmation.** After the deep-link sign-in (not the loopback one), the app tells the relay how it ended: `POST {RELAY}/intervals/oauth/result` with `{"state","ok"}`, unsigned (the app has no device key yet; the random state known only to the browser and the app is the secret, the relay keeps only its hash for 10 minutes, first write wins). `ok` is true once the code is exchanged and the token kept (a failed device registration does not count against it) and false when the exchange fails; a state that does not match is not reported, as it is untrusted. The report goes through `net.http`, best effort with a 4 s time-out, and is never awaited by the connect. The relay's bounce page polls `POST /intervals/oauth/status` and shows "Connected. You can close this page." only then, so that following the link does not count as success. The Tauri http scope gets the exact URL `https://ridrs.app/intervals/oauth/result`. intervals.icu accepts `ridrs://` as a redirect URI, but its confirmation dialog then stays open, so the https relay redirect stays.

The `external_id` of an upload is `linkIdOf(sessionId)` (every character outside `[A-Za-z0-9._-]` becomes `_`, at most 128), because the ids of the host hold colons and the relay accepts only that pattern. The same mapping names a ride in a link, resolves a link to its session, and is the `externalId` of the rides of this device in the done-workouts merge (ADR 0076).

## Consequences

- New dependencies `@noble/*`, `tauri-plugin-deep-link` (Rust and JS), and the relay's origin in the Tauri http scope.
- The relay's redirect URI has to be registered with the intervals.icu OAuth client before the deep-link sign-in works.
- The upload does not write the link `https://ridrs.app/activities/<external_id>` into the description: the OpenAPI spec of intervals.icu was not read (no call to it was allowed), so it is not known whether the upload takes a `description`.
- An account connected before this version has no device until the rider connects again.
