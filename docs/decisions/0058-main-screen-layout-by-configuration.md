# ADR 0058: The Main Screen's Layout by Configuration

Status: accepted on 2026-11-05 (decisions L1–L9 of the main screen layout brief, chosen by the maintainer) and implemented the same day. Amended on 2026-11-06 at the maintainer's request: the menu stays while the device setup is shown (screens in the content area). Extended by [ADR 0059](0059-app-areas-as-a-clickable-preview.md): global actions (`main/action`), the areas, Home renamed Today, Devices moved from the menu to the actions. Amended by [ADR 0071](0071-global-screens-in-a-dialog-over-the-page.md): the layout names the screens shown in a dialog over the page (`dialogs`).

## Context

The main screen stacked a title, Start ride and two extension points (`main/status`, `main/panel`) in one column, and every contribution of a point was shown. The maintainer's design draft is a dashboard: a menu on the left, a top bar, and tiles in a 12-column grid that span different widths. Which plugin fills the menu, the top bar and each tile should be configured, not coded, and every part should be a plugin of its own.

The shell's `ctx.slot(point, container)` mounts all contributions of a point into one container, in registry order. A grid needs one contribution per cell, in an order and width that the contributions do not decide themselves.

## Decision

- **`ui-main-screen` is the layout.** Its screen `main` offers `main/menu`, `main/top-bar` and `main/tile`, draws nothing but the grid and keeps navigating to `activity` on `activity.state-changed`. `main/status` and `main/panel` are gone.
- **One contribution per slot: `ctx.slot(point, container, { contribution })`.** With the key `<pluginId>/<contributionId>` (the wrapper's `data-contribution`), the shell mounts only that contribution, once it targets the point, and keeps it in sync: mounted when its plugin starts, unmounted when it stops. A key of a contribution to another point mounts nothing and logs a warning. Without the option, nothing changes. The core and the registry do not change.
- **The layout document** `plugins/ui-main-screen/layout.json` (L1), validated with zod by the screen (`layoutSchema`, strict): `version` 1, the `menu` and `topBar` contributions, the `screens` of the content area (default none) (each optional: left out, the area is not drawn), and `tiles` in order, each with its `columns` of 12 at `wide` (required) and `medium` (defaults to `wide`). A contribution may be placed once. An invalid document fails the screen (`client-load-failure`); it does not guess. The manifests still say which point a contribution *can* fill (rule 6); the layout says *whether and where* it appears (L2): a contribution to `main/tile` that the layout does not name is not mounted; a named one whose plugin does not run takes no cell and appears once it starts. No rider editing and no per-app layouts until the athlete profile (P7).
- **Empty tiles leave no gap.** A cell whose contribution renders nothing (the interrupted ride without one, a stopped plugin) is `hidden`; a `MutationObserver` follows it.
- **Breakpoints by the window's width** (L5), through media queries, on the layout's root as `data-breakpoint`: `wide` from 1200 px (menu with labels, top bar), `medium` from 768 px (menu as an icon rail, top bar, the medium spans), `compact` below (no top bar, the menu as a bottom bar, every tile spans 12). The brief named the root's width (`ResizeObserver`); the main screen fills the window, so the window's width is the same and media queries are what a headless DOM can resize.
- **Look as a contract** (L7). The layout sets design tokens as CSS custom properties on its root: `--ridrs-bg`, `--ridrs-surface`, `--ridrs-surface-raised`, `--ridrs-line`, `--ridrs-text`, `--ridrs-text-muted`, `--ridrs-accent`, `--ridrs-accent-text`, `--ridrs-info`, `--ridrs-ok`, `--ridrs-warn`, `--ridrs-focus`, `--ridrs-radius`, `--ridrs-gap`. Contributions draw their own cards with them, with fallbacks, and may style by `[data-breakpoint]`. Like event ids, the names are a public contract.
- **The menu** `ui-main-menu` (L3, L4) contributes `menu` to `main/menu` and offers `menu/item`. Its own entry Home is the main screen and always `aria-current="page"`; every other entry is a contribution of the plugin that owns the screen (today `ui-devices`: Devices → `setup`). An entry is one `button[data-menu-item]` with an icon `[data-menu-icon]` (painted from the CSS variable `--icon`) and a label `[data-menu-label]`; the menu styles them all. The entry of the shown screen is `aria-current="page"`; every entry follows `ctx.onNavigated`.
- **Screens in the content area** (amendment of 2026-11-06, replacing "the menu on the main screen only" of L3): the layout names the screens that the main screen shows in its content area instead of the top bar and the tiles (`"screens": ["setup"]`). The main screen controls its content: it hands that list to the shell with `ctx.outlet(container, { screens })`, and while it is the screen in the root, navigating to a named screen mounts that screen into the outlet and keeps the main screen, and so the menu, mounted around it. Navigating back to `main` brings the top bar and the tiles back (they are unmounted meanwhile). Navigating to a screen the layout does not name (`activity`), or to a named one while the main screen is not shown, shows it on its own, as before. One level only: an outlet only of the screen in the root. `ctx.onNavigated(handler)` tells every component the shown screen (the one in the outlet, not the main screen around it). The screens themselves know nothing of this: a screen stays a plain screen, and the main screen's code names none of them; only its configuration does, as it does the tiles. A first version let a screen name its frame in its manifest (`"frame": "main"`); the maintainer rejected it, because the device setup then knew the main screen.
- **The top bar** `ui-main-top-bar` greets by the local time of day ("Good morning" 5–11 h, "Good afternoon" 12–17 h, "Good evening" otherwise), refreshed on the hour. Rendering only; no name before an athlete profile exists (L8).
- **Tiles today**: `ui-ride-recovery/interrupted-ride` (12), `ui-tile-ride-start/ride-start` (new plugin: Start ride and the ride-saved notice, moved out of the screen; 8, medium 12), `ui-devices/devices` (the devices tile replaces the indicator: one row per kind that opens that kind's details in `setup`, and All devices or Set up your devices; 4, medium 6), `ui-training-plan/next-workout` (6).
- **Keyboard** (L6): reading order is menu, top bar, tiles in layout order; ADR 0045 is unchanged. No two-dimensional navigation across the grid yet.
- New plugins are AGPL-3.0-or-later; `@ridrs/ui-sdk` stays Apache-2.0 (L9). Icons are Lucide 1.55.0 files (ADR 0047): `house` (menu), `bluetooth` (Devices), `play` (Start ride).

## Consequences

- A tile is added by a plugin that contributes to `main/tile` **and** an entry in `layout.json`; a plugin alone shows nothing on the main screen.
- `ui-main-screen` depends on `zod` for the layout schema.
- The devices tile asks the setup for a kind's details through a variable in the plugin's one client module (`details-request.ts`); `navigate` still takes no parameters.
- Not built (L8): recommendations, training week, last activity, progress, search, notifications, avatar, images, i18n, row spans and editing the layout.
- `@ridrs/ui-sdk` gains the context methods `onNavigated` and `outlet` (with `OutletOptions`); manifests, the registry and the core do not change. A screen is moved into the content area by an entry in `layout.json` alone.
- Tests: `main-screen-layout.feature`, `main-menu.feature` (with the menu that stays beside the device setup), `devices-tile.feature` (formerly the indicator), unit tests of the layout schema, the breakpoints and the greeting.
