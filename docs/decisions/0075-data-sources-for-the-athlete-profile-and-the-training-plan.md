# ADR 0075: Data Sources for the Athlete Profile and the Training Plan

Status: **accepted** on 2026-11-08 by the maintainer ("Accept all as proposed": every point the proposal left open is decided as proposed), from the proposal [athlete-data-sources.md](../ideas/athlete-data-sources.md), on the maintainer's request ("pick p7, p8. p9 should be only intervals.icu. add an interface for different data types, that can be implemented by sync providers. add data source settings to the existing settings page"). Stage D0 of that proposal; D1 and D2 are built (2026-11-08), D3 and D4 (2026-11-09); of D5 the calendar read and the library read are built (2026-11-09), the calendar write is not; see "Implementation". Amends [ADR 0052](0052-persistence-domains-and-plan.md) (no SQLite and no profile history in P7) and [ADR 0060](0060-equipment-garage-and-the-frozen-bicycle.md) (the bicycle stays out of the athlete profile).

## Context

ADR 0052 left P7 (local athlete profile), P8 (local calendar) and P9 (providers) for later. Today:

- `planner-intervals-icu` reads the athlete (FTP, weight, LTHR, max HR) and 14 days of planned rides into one app state `training.plan`, keyed by the closed enum `trainingServiceSchema = ['intervals.icu']` ([ADR 0048](0048-intervals-icu-connection-and-training-plan.md), [ADR 0068](0068-app-state-and-services-beside-the-bus.md)).
- FTP and weight in the Me area and the calendar in the Training area are previews on user documents ([ADR 0059](0059-app-areas-as-a-clickable-preview.md)); nothing reads them.
- `physics-rider` uses a fixed 75 kg (`origin: 'default'`). The bicycle already enters a ride as an input and is frozen by `activity-session` (ADR 0060).
- The settings page chooses among a few options with a row of chips (`pv-chip`, `aria-pressed`), not with dropdowns.

The maintainer wants a source per data type chosen on the settings page from every provider that offers it, and workouts read from all providers.

## Decision

### Names and data types

- **Data sources, not sync providers.** A data type has one source of truth; nothing is copied or merged between stores, and switching the source copies nothing. Sync stays P10. (Name: maintainer.)
- **Three data types:**

  | Data type | Topic | Access | Source |
  |---|---|---|---|
  | Athlete profile (FTP, weight, LTHR, max HR; the name read only) | `athlete.profile` | read and write | one, chosen |
  | Planned workouts (the calendar) | `training.calendar` | read and write | one, chosen |
  | Workout library | `training.library` | read | all providers at once |

### The interface

- **On the app state and services of ADR 0068**, no new channel and no new manifest field. `defineDataType(id, dataSchema, writes)` in `@ridrs/contracts` (Apache-2.0) defines, the same way for every type:
  - the topic `<id>`, **keyed by the provider id** (`ridrs`, `intervals.icu`; manifest id pattern); its value is `{ provider, label, status: 'ready' | 'offline' | 'unavailable' | 'loading', writable, fetchedAt?, data? }`. The keys of a topic are the providers of that type: a provider offers a type by owning its key (`state.owns` in its manifest, rule 6).
  - one service per write (`athlete.profile.update`; `training.calendar.plan`, `.move`, `.remove`), **keyed by the topic**, so the host routes a write to the provider that owns the key. A provider that cannot write answers `read-only`; one that cannot reach its service answers `unreachable`.
- `trainingServiceSchema` becomes an open provider id. `training.plan` is removed: its athlete goes to `athlete.profile`, its workouts to `training.calendar`. `training.account` and its services (`connect`, `disconnect`, `refresh`, `upload`) stay: an account belongs to a provider, not to a data type.
- **The choice** is the app state `data.source`, keyed by the data type (`athlete.profile`, `training.calendar`), value `{ provider }`, with the service `data.select`. Its owner keeps it in the user document `data-sources`. The library has no choice.

### Providers

- **ridrs (this device)**, a new plugin `profile-local` (type `storage`, `"persistence": ["user"]`): always `ready` and writable. The profile is the user document `athlete` (version 1: `ftp`, `weight`, `lthr`, `maxHeartRate`, `changedAt`), migrated once from the Me area's `preview` FTP and weight. The calendar comes from the Training area's entries (P8). It is the default source of every type, so a choice is never empty.
- **intervals.icu**, the existing `planner-intervals-icu` (id, secret key and cache path unchanged), owns the key `intervals.icu` in all three topics:
  - Profile read as today; weight from today's wellness record, else `icu_weight`.
  - Profile write: weight to `PUT /api/v1/athlete/0/wellness/{today}`, FTP to `PUT /api/v1/athlete/0/sport-settings/Ride`, into the field it was read from (`indoor_ftp` if set, else `ftp`). `icu_weight` is not written (maintainer).
  - Calendar read as today (`GET …/events`); writes as `POST`, `PUT` and `DELETE …/events`.
  - Library read from `GET /api/v1/athlete/0/workouts` (and `…/folders` for the grouping).
  - New scopes for the writes and the library, expected `WELLNESS:WRITE`, `SETTINGS:WRITE`, `CALENDAR:WRITE`, `LIBRARY:READ`; **to be confirmed** against intervals.icu's OAuth documentation before stage D4 (the OpenAPI spec names none per operation). Older tokens get 403 and the rider reconnects, as in [ADR 0064](0064-ride-debriefing-and-activity-upload.md).
- **Writes are refused, not queued**, when a source cannot be reached; the UI keeps the old value and says why. A queue would be sync.
- **The first start of this version** selects intervals.icu for the profile and the calendar when its account is connected, so the next-workout card keeps showing the intervals.icu plan.

### The ride

- **The profile enters a ride as an input** (AGENTS.md rules 7 and 13), as the bicycle does: the owner of `data.source` watches the chosen profile and accepts `athlete.profile-changed { provider, ftp?, weight? }` (no name) at host start and after every change. `activity-session` freezes it with the lifecycle event `activity.athlete { sessionId, athlete }` right before `running`, beside `activity.equipment`. A change during a ride applies to the next one.
- **`physics-rider`** subscribes to `activity.athlete` (rule 11) and takes the frozen weight with the new origin `'profile'`; without it, 75 kg as before. The recording's pre-roll keeps the latest `athlete.profile-changed`; a continued ride re-enters it from the journal (ADR 0057).
- The chosen source unavailable without a cache: the ride uses the defaults, and Today's start card says so; the ridrs profile is not used in its place, since that would mix two sources (maintainer).

### The settings page

- A section **"Data sources"** in `ui-settings` with one row per data type. The profile and the calendar offer **one chip per provider** (the topic's keys), the chosen one pressed, and beside it the source's status ("Connected as …", "Offline · last loaded …", "Not connected" with Connect, which calls `training.connect`). The library row lists its providers and is not a choice. During a ride, a change says that it applies from the next ride.
- **Chips, not a dropdown** (rule 12): a focused native `<select>` takes the arrow keys, and its open list differs per platform. A picker screen replaces the chips only if a type has more than about four providers. (Chips: maintainer.)
- The Me area's FTP and weight show the chosen source's values and write through `athlete.profile.update`.

### Later

- **No SQLite and no effective-dated history** in P7: a ride freezes its own values, and intervals.icu keeps its own history. Both wait for a use case (charts of FTP or weight) behind the same access.
- **The calendar write** is "plan a library workout on a day" (with its steps), then move and remove. The Training area's own entries (rest, note, outdoor) stay in the ridrs calendar and are not written to intervals.icu (maintainer).
- **Built-in ridrs workouts**: not in these stages (maintainer); the ridrs library stays empty until riding a workout gives them a use, then they ship as files like the drivetrain specifications.
- **Riding a workout** (steps to `trainer.target-power` inputs with the frozen FTP), the use case that makes the library and the calendar worth more than a list: proposed as the next stage, with its own ADR.
- **Ride uploads as a data type** with chosen targets, once a second target exists.
- The bicycle stays a ridrs-only user document, not part of the profile.

### Stages

Each starts with failing scenarios (rule 1); scenarios as in the proposal, section F.

1. **D1** `defineDataType`, `data.source`, `data.select`, the settings section, a test fixture with two providers.
2. **D2** `profile-local` (profile), the real Me area, `athlete.profile-changed`, `activity.athlete`, `physics-rider` from the profile. No network.
3. **D3** intervals.icu as a profile source; `training.plan` split; the first-start selection.
4. **D4** writing the profile to intervals.icu (scopes).
5. **D5** planned workouts and the library from both providers, the next-workout card from the chosen source, planning a library workout on a day.

## Consequences

- New: `defineDataType`, the topics `athlete.profile`, `training.calendar`, `training.library`, `data.source`, the services `data.select`, `athlete.profile.update`, `training.calendar.plan`/`.move`/`.remove`, the events `athlete.profile-changed` and `activity.athlete`, the origin `'profile'`, the plugins `profile-local` and the owner of `data.source` (the host side of `ui-settings`, or a plugin of its own). Removed: `training.plan`, the enum `trainingServiceSchema`.
- `packages/contracts/src/app-events.test.ts` gets `athlete.profile-changed` as a simulation input, not as an app event.
- The rider's weight changes physics results: rides recorded before D2 replay with 75 kg, as they were ridden.
- Recordings hold the rider's FTP and weight (not the name) from D2 on; they are the rider's own local files.
- Writes to intervals.icu change the maintainer's real account until the OAuth client is approved; the scenarios run against the simulated intervals.icu only.

## Implementation

- **Stage D1 (2026-11-08): the interface and the choice.** Contracts (`@ridrs/contracts`, Apache-2.0): `data-sources.ts` (`defineDataType`, `DataSource`, `providerIdSchema`, `DEFAULT_PROVIDER`, the write answer `dataWriteResultSchema`, the app state `data.source` and the service `data.select`) and `athlete.ts` (`athleteProfileSchema`, `athleteProfileType` with the topic `athlete.profile` and the service `athlete.profile.update`, the input `athlete.profile-changed`, the lifecycle event `activity.athlete`). The new topic, services and events are registered in `apps/native/src/compose.ts`, `apps/headless/src/main.ts` and the test World. The owner of `data.source` is the **host side of `ui-settings`** (no new plugin): it keeps the choice in the user document `data-sources` (`plugins/ui-settings/data-sources.ts`), sets `data.source` for the data type `athlete.profile` at start, and provides `data.select`. The settings page has the section "Data sources" with the row "Athlete profile" (one `pv-chip` per key of the topic, ridrs first, the chosen one pressed, the status beside it; English and German; the note that a new source applies from the next ride while a ride is under way). The new React hook `useStateEntries` (`@ridrs/ui-sdk/react`) gives a UI plugin a topic's entries. The test fixture `tests/fixtures/plugins/data-source/fixture-transport-athlete` is a second provider (`fixture-cloud`, read only, ready, offline or unavailable as a scenario sets it). Scenarios: `tests/features/ui/data-sources.feature` (settings lists every provider and shows the chosen one and its status; choosing hands the provider's profile to the next ride; the choice is kept when ridrs restarts; a provider that goes away is replaced by ridrs, also after a restart without it; an offline and an unavailable provider; an unavailable source gives the ride the defaults and the start card says so; the choice with the keyboard alone; German; the note during a ride), steps `tests/steps/data-sources.steps.ts`, Vitest `packages/contracts/src/data-sources.test.ts`.
- **Stage D2 (2026-11-08): the local profile in the ride.** The plugin `profile-local` (type `storage`, `"persistence": ["user"]`, AGPL-3.0-or-later; `plugins/profile-local/`) owns the key `ridrs` of `athlete.profile` (always `ready` and writable, `data: {}` without values) and provides `athlete.profile.update` for it; the user document `athlete` v1 (`ftp`, `weight`, `lthr`, `maxHeartRate`, `changedAt`; `athlete.ts`). A change takes effect at once and is kept after it, as the language is. `ui-area-me`: its client shows and changes FTP and weight of the chosen source through `athlete.profile.update` (a read-only source disables the buttons, a refused change says why; an unset value shows "–" and its first step starts from 200 W or 75 kg) and no longer keeps them in `preview`; its host side hands the old `preview` FTP and weight to the profile once (below). The host side of `ui-settings` watches the chosen profile and accepts `athlete.profile-changed { provider, ftp?, weight? }` once the host has started and after every change, and again when a ride finishes (the garage's pattern, for the next ride after a continued one). `activity-session` freezes the latest one as `activity.athlete` right before `running`, after `activity.equipment`; `physics-rider` takes its weight with the new origin `profile`, else 75 kg (`default`), and its `config.snapshot` section reports it. `recording-session` keeps the latest `athlete.profile-changed` in the pre-roll like the bicycle. Today's start card (`ui-tile-ride-start`) says that the next ride uses default values when the chosen profile is unavailable and has no data. `athlete.profile-changed` is a simulation input in `packages/contracts/src/app-events.test.ts` (and has samples in `recording.test.ts`); the Vitest `physics-plugins.test.ts` lets `physics-rider` listen to `activity.athlete` only. Scenarios: `tests/features/athlete/athlete-profile-in-the-ride.feature` (65 kg climbs faster than 85 kg at 200 W on 5 %: 16.45 and 13.57 km/h; no profile, 75 kg; the profile handed over at host start and after a change; a change during a ride applies to the next one; the chosen source's weight is the ride's; a source that cannot be read gives the defaults; the recording reports the frozen weight; the replay uses the recorded weight; the pre-roll keeps an athlete handed over two minutes before the ride; a recording without a profile replays with 75 kg; a continued ride keeps its weight; the next ride after a continued one uses the profile as it is now) and `tests/features/ui/athlete-profile-in-me.feature` (no values; a change is kept, handed to the ride and still there after a restart; Me's old FTP and weight are handed over once; a read-only source's values; an unreadable source), steps `tests/steps/athlete.steps.ts`.
- **Stage D3 (2026-11-09): intervals.icu as a source of the athlete profile.** `planner-intervals-icu` owns the key `intervals.icu` of `athlete.profile` and of the new `training.calendar` (`trainingCalendarType` in `training.ts`, workouts only, no write services yet) beside `training.account` and `training.upload`; `training.plan`, `trainingPlanSchema` and `trainingAthleteSchema` are gone, and `trainingServiceSchema` is a provider id. The profile is read as before, its weight from today's wellness record (`GET …/wellness/{today}`), else `icu_weight`, and its FTP rounded to whole watts. Both keys are `loading` from the plugin's start, then `ready`, `offline` (the cache, with its `fetchedAt`) or `unavailable` (no account, a rejected token, or unreachable without a cache), and then carry no data. The cache file keeps its path and now holds `{ fetchedAt, athlete, workouts }`; a cache from before is still read. `ui-training-plan` builds its plan from the calendar and the profile of the key `intervals.icu`. The host side of `ui-settings` chooses at the first start (no `data-sources` document yet): once every provider has started and none is `loading`, a provider whose `training.account` is `connected` is chosen for the profile, and the document is written either way, so connecting later changes no choice. Scenarios: `tests/features/ui/athlete-profile-from-intervals-icu.feature` (first start with and without an account; a choice is kept; connecting later; wellness weight, its absence on today's date, indoor FTP; the next ride's weight; offline; disconnected, with defaults and no fallback to ridrs; a rejected token), steps in `tests/steps/training.steps.ts`, the simulated intervals.icu answers the wellness record. The existing training scenarios run on the split topics unchanged.
- **Stage D4 (2026-11-09): writing the profile to intervals.icu.** `planner-intervals-icu` provides `athlete.profile.update` for its key: a weight goes to `PUT /api/v1/athlete/0/wellness/{today}` (`{ weight }`), an FTP to `PUT /api/v1/athlete/0/sport-settings/Ride` into the field it was read from (`ftpField` in `intervals.ts`, kept in the plugin and in the cache file), and `icu_weight` is never written. The shown profile follows an accepted change at once (and the cache), without a reload. A write that cannot reach the service, or that the service answers with an error, is `{ ok: false, reason: 'unreachable' }` and changes nothing; a 401 or 403 forgets the token as an upload does (ADR 0064), sets the account to `failed` with `token-rejected` (the Me area offers "Reconnect intervals.icu"), answers `read-only`, and keeps the last profile and calendar shown, `offline` and not writable until the rider connects again. The scopes asked for are now `SETTINGS:WRITE,CALENDAR:READ,WELLNESS:WRITE,ACTIVITY:WRITE`. Scenarios: `tests/features/ui/athlete-profile-to-intervals-icu.feature` (the scopes; a weight and an FTP written; the indoor FTP where one is set; no change of the athlete's own weight; 403 and reconnecting; unreachable, also offline), Vitest `ftpField`; the simulated intervals.icu takes the two `PUT`s and can answer them with 403 or not at all.
- **Stage D5, calendar read (2026-11-09): the choice of the planned workouts.** `data.source` and `data.select` now serve two data types, `athlete.profile` and `training.calendar` (the host side of `ui-settings`, which also chooses a connected service at the first start for both). The settings page has the row "Planned workouts" (English and German) beside the profile's, one component for both rows. `planner-intervals-icu` already served its key of `training.calendar` (D3). The provider `ridrs` is the host side of `ui-area-training`: it publishes the workouts of the area's calendar (`plannedWorkouts` in `calendar.ts`: the entries of kind workout on their day of the week of today, from today on, without steps) from the document `preview` at start and after every change the client hands over with the new service `training.calendar.hand-over`. `ui-training-plan` shows the card and the details of the chosen calendar source (ridrs on this device has no account to connect). Scenarios: `tests/features/ui/calendar-source.feature` (the row and its providers; without an account the Training area's next workout; the first start chooses intervals.icu; the card follows the choice; the choice is kept; a change in the Training area reaches the card; offline; German), Vitest `calendar.test.ts`.
- **Stage D5, library read (2026-11-09): the workout library of every provider.** `trainingLibraryType` (`training.library`, `libraryWorkoutSchema`: a planned workout without a date, with the `folder`) is read only. `planner-intervals-icu` loads `GET /api/v1/athlete/0/workouts` and `…/folders` with the profile and the calendar (`toLibrary` in `intervals.ts`: cycling workouts only, each with the name of its folder or plan, ordered by folder and name; the cache file keeps the library as well) and asks for `LIBRARY:READ`; a 403 leaves only the library `unavailable`. The host side of `ui-area-training` offers the key `ridrs` with no workouts (no built-in workouts, ADR 0075). The settings page has the read-only row "Workout library" listing the providers, and the Training area a section "Workout library" with the workouts of each provider (name, folder, minutes, TSS). Scenarios: `tests/features/ui/workout-library.feature` (the row; the two requests; the workouts with their folders and no runs; a token without the scope; offline; disconnected; German), Vitest `toLibrary`.
- **Decisions the implementation made where this ADR left room:**
  - **The ridrs calendar is handed over by the Training area, and read only for everyone else.** The area's entries are a document of the area's client module, which the area edits in memory and writes whole; a write from another side would be overwritten. The area therefore tells its host side after each change (`training.calendar.hand-over`, a contract in `training.ts`), and the key `ridrs` of `training.calendar` is `writable: false`: the library's "Plan on a day" (below) is refused there with `read-only`, and the area's own "Schedule … on …" buttons stay the way to plan on this device. Entries are by weekday of this week, so the dates are those of the week the app handed them over in.
  - **Until a source has a calendar, the card is intervals.icu's.** Where the chosen source offers no calendar at all (the Training area is not composed), `ui-training-plan` keeps showing intervals.icu with its Connect button, so the main screen's offer to connect stays where ridrs has no calendar.
  - **A 403 on a write keeps the data shown** (status `offline`, not writable) instead of clearing it as a rejected token on a load does: nothing was lost, and "old value kept" holds. A source that is `offline` because it cannot be reached stays writable, so a change is tried and refused with the reason.
  - **The OAuth scopes are confirmed** against intervals.icu's OAuth support thread (https://forum.intervals.icu/t/intervals-icu-oauth-support/2759, read 2026-11-09): scopes are `ACTIVITY`, `WELLNESS`, `CALENDAR`, `CHATS`, `LIBRARY` and `SETTINGS`, each as `:READ` or `:WRITE`, `WRITE` includes `READ`, comma separated. Each stage asks for what it uses: D3 adds `WELLNESS:READ` (the wellness weight; a token without it gets 403 there, which only leaves `icu_weight` in its place and does not reject the token).
  - **`training.calendar` exists from D3** with the workouts of the old plan and no write services (they come with D5), and the next-workout card and the workout details read the key `intervals.icu` until D5 lets the card follow the chosen calendar source. The details show the FTP and weight of the profile of that key.
  - **The first-start choice looks at `training.account`**, not at a provider's status: a fixture or any other ready provider without an account is never chosen on its own.
  - **A refused write is an answer, not an error.** The write services answer `{ ok: true }` or `{ ok: false, reason: 'read-only' | 'unreachable' }` (`DataWriteResult`) instead of failing with a code: the set of error codes is closed in `RidrsError`, and a refusal is an expected answer the UI shows.
  - **The hand-over of Me's old values** goes through `athlete.profile.update`, from the host side of `ui-area-me` after `core.host.started`: a plugin's settings documents are its own (`config/user/<plugin id>/`), so `profile-local` cannot read `preview`. Only after an `ok` answer does `ui-area-me` rewrite `preview` without `ftp` and `weight`, so it happens once; without a profile provider or on a failed call the values stay for the next start. Without a `preview` document the profile on this device starts empty (no values), not with the old placeholders of 200 W and 72 kg, so a rider who never entered a weight rides with the default 75 kg. Reviewed the same day: the preview wrote 200 W and 72 kg as soon as anything in Me changed, so these exact values are not handed over (a rider who really had 72 kg enters it again); and a profile on this device that already holds an FTP or a weight is never replaced, the old values are only dropped (`ui-area-me` watches `athlete.profile`). So a hand-over whose rewrite of `preview` failed cannot overwrite a later change at the next start. Scenarios: "Me's old placeholder values are not handed to the profile" (three examples), "Me's old values never replace a profile that already has values".
  - **The choice outlives its provider.** When the chosen provider's key is gone (a plugin removed or stopped), `data.source` and the page show ridrs, but the document keeps the rider's choice, so the provider returns with its plugin. The check starts with `core.host.started`, because providers start one after another.
  - **`athlete.profile-changed` also goes out without values** (`{ provider }` for an unavailable source), so the ride records where its defaults came from; it goes out only if the provider in use has an entry at all.
  - **The configuration snapshot is taken a microtask after `running`.** The recorder sees `running` when it is published, before the plugins have the frozen bicycle and athlete published just before it, so the `config.snapshot` section of `physics-rider` showed the defaults (the bicycle's, which ADR 0060 promises to be frozen, takes the same path). `recording-session` writes nothing of a new ride until the snapshot is taken.
  - **ridrs is named in the UI's language** ("ridrs (this device)", "ridrs (dieses Gerät)") by the plugin that shows it; the name of any other provider is the `label` its plugin gives.
