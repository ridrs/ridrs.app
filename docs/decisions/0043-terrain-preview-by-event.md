# ADR 0043: The Terrain Ahead by Event (`world.terrain-preview`)

Status: partly superseded by [ADR 0044](0044-ui-landscape-as-world-sensor-and-spatial-layer.md) (2026-11-04): the host world `physics-road`, its demo course and the subscription in `physics-virtual-speed` are gone; the landscape lives in the UI and the physics reads the terrain from the spatial layer. Still valid: `world.terrain-preview` in metres along the path, anchored at the physics odometer, the 1 m grid, linear gradient interpolation and the replay rule "not in recording".

Amends [ADR 0027](0027-road-gradient-and-environment.md) (the road capability) and [ADR 0026](0026-physics-model-and-fixed-step.md) (only the engine has events; step 0 timing).

## Context

The integrator pulled the road with the synchronous `single` capability `physics.road` (`at(distance)`), so the road had to be a function the physics could call at any distance. A world (a demo course today, a route or terrain later) knows the terrain; the physics knows how far the rider went. The terrain ahead should reach the physics as data the world pushes, without the physics requiring a world. This ADR converts only this one capability; every other capability stays as it is.

## Decision

- **Event, in metres.** Contract `world.ts` (Apache-2.0): `world.terrain-preview { revision, originDistance, spacing, samples: [{ gradient }] }`, at least two samples. Sample `i` lies at the odometer reading `originDistance + i · spacing`; gradient is rise over run, like `RoadSample.gradient`. Distance, not time, is the unit: the terrain does not depend on speed, so the world can publish it exactly, and the uncertainty of the speed stays in the physics. A time window would also be a forecast, which the temporal layer does not hold. `revision` counts up per world and is unused by the physics today (it takes the newest window); it is there for later re-planning (steering) at no cost.
- **The physics keeps the odometer.** `physics-virtual-speed` subscribes to the event (it requires nothing for it), keeps the newest window and, once per step, interpolates **linearly** at the previous distance: `s = (odometer − originDistance) / spacing`. It validates the gradient as before (finite, ±30 %); an invalid one fails the step naming the publishing plugin (the envelope's `source`, which replaces `RoadCapability.source`).
- **Fallback.** Outside the window (none yet, or run out) the physics holds the last gradient it used, flat (0) at the start of every ride, and reports `terrain-preview-missing` (new diagnostic code; details: `distance`, `at`, `reason: no-window | outside-window`, held `gradient`) **once per gap**; a covering window closes the gap. A missing world is found at run time this way, not by capability resolution. **No marker capability** (`world.terrain`): nothing in the code needs one, and a `single` marker would block several worlds side by side.
- **The world: `physics-road` becomes the demo course world** (same id, type `world`, provides only `config.snapshot`). Keeping the id means a recording's plugin set (recordings name plugins by id) still includes the world on replay; a new plugin would be disabled when an older recording is replayed, and the physics would ride it flat. It publishes a window from 0 m when a ride starts (`running`), then on each `physics.state-batch` of that ride when less than half of the current window is ahead of the batch's last distance. It reads the odometer from the batch and never integrates distance; at standstill the distance does not change, so it publishes nothing. Windows start at the grid point at or before the odometer (`floor(d / spacing) · spacing`): samples lie on one fixed grid, so the interpolated gradient at a distance is the same whichever window covers it. Snapshot section: `course` and `terrain` (`windowLength`, `spacing`).
- **Numbers: window 20 m, spacing 1 m (21 samples), republish below 10 m left.** In the same turn as a batch, the world's window arrives before the next step, so the in-process latency is zero; the window must cover the distance between two batches (50 ms): 1.25 m at 25 m/s (90 km/h, above the demo course's 58 km/h). The 10 m half-window covers 400 ms at 25 m/s: eight batches, and room for a future asynchronous world (200 ms ≈ 5 m). 1 m is below a bike length; a finer grid does not change settled speeds (measured, see below) and multiplies the payload. At 34 km/h that is about one event per second of 21 samples, small next to 20 `physics.state-batch` per second in a recording.
- **Step 0 (option a).** `physics-engine` computed step 0 inside its own reaction to `activity.state-changed` → `running`; whatever a world publishes in reaction to the same event is delivered after it, in every plugin order. The engine now computes step 0 as a task at `startedAt` (`ctx.clock.scheduleAt`), which runs after the turn and before any input of the same time ([time-and-scheduling.md](../architecture/time-and-scheduling.md)): the first window is there. States, timestamps and envelope ids are unchanged (same logical time; ids count per source and millisecond). A finish request is an input of its own, so step 0 always runs before a ride can finish. Option (b), the flat fallback for step 0, was rejected: it is right only on a course that starts flat, and step 0 would need a silent exception to the diagnostic. Scenario: a probe world at 5 % gives step 0 at 5 % with no diagnostic; with step 0 back in the reaction (mutation) it fails.
- **Older recordings.** The replay compares per `(type, source)`; a recording made before this change has no `world.terrain-preview`, so the replayed windows would be reported as added. The comparison now **does not compare an event type that occurs nowhere in the recording** and lists such streams in `notCompared` (`reason: 'not-in-recording'`, replayed count; the CLI prints them as `uncompared`). `identical` covers every compared stream. A type the recording contains is compared from every source, including new sources, as before. ADR 0029 and the format v1 require a recording to hold every bus event as published; they do not require a reader to know every type a later ridrs publishes. This is a comparison rule, not a format change: no new field, `formatVersion` stays 1.
- **Removed:** `physics.road`, `RoadCapability` and `physicsRoadCapability`, and their registration in the composition roots and tests: after the change nothing uses them. `RoadSample` stays: it is still the sample the forces get in `ResistanceInput` and that `physics.state` reports (`origin: 'default'`).

## Consequences

- **Measured differences** (200 W, fake time, 1 m samples against a step-like 1 mm grid; as the spacing goes to 0 the old values come back exactly): settled speeds are unchanged: 34.217 km/h flat, 14.898 km/h on 5 %, 57.823 km/h at the end of the −5 % descent; the constant-gradient scenarios are unchanged. At a segment boundary the gradient ramps in over the metre before it (e.g. 1999 → 2000 m: 0 → 5 %), so the climb starts about half a metre earlier: "flat for 100 m, then 5 %" at +20 s gives 25.51 km/h instead of 25.60, and the demo course at +300 s is at 2375.63 m instead of 2375.92 m. Both scenarios were updated with the cause noted in the feature. Later, the descent's ramp makes up for it (−0.01 m at +700 s).
- `physics-virtual-speed` is the first physics contributor with a subscription; it still publishes nothing and has no timer. `physics-engine` remains the only clock-driven physics plugin.
- Recordings contain the windows (about one event per second while moving); a replay compares them like every derived event.
- An older recording that crosses a segment boundary of the demo course replays with differing physics states from that boundary on: a real difference of the model, reported as such.
- Limit of the comparison rule: a recording that has no event of a type at all cannot check it. This also applies when the recorded run stopped before publishing a type, for example a failed physics step at step 0; its diagnostics show that.
- Out of scope, no use case yet: steering, pose, route position, elevation profile, surface/Crr, 2D/3D worlds, obstacles, and every other capability.
