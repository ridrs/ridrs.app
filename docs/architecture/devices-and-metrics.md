# Devices and Metrics (Phase 2)

```text
transport-ble-noble  --ble.central-->  device-ftms-trainer
device-ftms-trainer  --device.connection-changed, measurement.power, measurement.cadence-->  metric-power, metric-cadence
metric-*             --metric.power, metric.cadence (+ latest())-->  output-console
```

- **Contracts** (`packages/contracts`): `ble.central` (UUIDs normalized to 4-char lowercase hex), the device/measurement/metric events and `MetricReading`.
- **Core extension**: `ctx.signal` is aborted by the host when a plugin stops; `ctx.reportDiagnostic` lets plugins report problems (`malformed-packet`, `multiple-sources`).
- **Device plugin** owns protocol bytes; nobody else sees them. FTMS carries no timestamp, so `measuredAt = receivedAt` with origin `receive`.
- **Metric plugins** know no device. The first delivering device is the active source; loss (`reconnecting`/`disconnected`) or 3 s of silence makes the metric `unavailable` - the last value is never kept. (Phase 4 replaces the fixed 3 s by a threshold that fits the source's rate; 3 s remains the fallback.)
- **Testing**: `packages/testing` holds the in-process BLE simulator (importable from `tests/**` only). `tests/fixtures/plugins/simulated-trainer` provides `ble.central` from it and plays a scripted ride.

## Phase 4: a second source, shared building blocks, derived metrics

```text
ble.central --> device-ftms-trainer --measurement.power, .cadence-->     metric-power, metric-cadence ─┐
ble.central --> device-heart-rate   --measurement.heart-rate-->          metric-heart-rate ────────────┤ series (ctx.temporal)
                                                    metric-power-heart-rate-ratio <── combine ─────────┘
```

- **Heart rate** (`device-heart-rate`): scans for the Heart Rate Service `180d`, connects to the first device found, subscribes to Heart Rate Measurement `2a37` and publishes `measurement.heart-rate` (bpm, `measuredAt = receivedAt`, origin `receive`). Flags (bit 0 value format, bits 1-2 sensor contact, bit 3 Energy Expended, bit 4 RR-intervals) are read per the Bluetooth SIG Heart Rate Service; energy and RR-intervals are only checked for their length. Contact supported but not detected, or a value of 0, is "no reading", not 0 bpm. A packet shorter than its flags require or an odd number of RR bytes is `malformed-packet`; the connection stays up. `device-ftms-trainer` and `device-heart-rate` each scan for their own service only and never take the other's device.
- **`@ridrs/ble-peripheral`** (`packages/ble-peripheral`, AGPL-3.0-or-later): the connection lifecycle extracted from `device-ftms-trainer` (scan → connect → subscribe → reconnect with `p-retry` → `device.connection-changed`), used by both device plugins; decoding stays in the plugin. It also holds `SharedBleScan`, which lets the Tauri and noble centrals serve several concurrent scans from the one scan their platform allows (the union of the requested services; each consumer sees only its own). blec ends its scan after two minutes and whenever it connects a device; `ble_scan` reports that on its `onEnded` channel, and `SharedBleScan` starts the scan again while a consumer is still searching.
- **Links and choices** ([ADR 0042](../decisions/0042-device-links-in-the-peripheral-link.md), [ADR 0046](../decisions/0046-one-link-per-device-and-signal-strength.md)): the link takes every `ble.central`, this device's Bluetooth (`route` `local`, the direct link) and the companion (`companion`). It scans over both; a device seen over both is listed once per link, each a device of its own with that link's id. The link pairs the two as `sameDeviceAs` when they have the same name, nothing in their advertising data tells them apart (manufacturer data by company, service data by service; a key whose bytes changed is left out), and the pair is unique either way ([ADR 0051](../decisions/0051-same-device-over-both-links-by-advertising-data.md)); the device setup shows a pair as one device. The pairing never changes what connects. The first device seen directly connects (one that only the companion saw waits 2 s for the direct link first). A lost link reconnects over the same link with backoff; there is no failover. `device.connection-changed` names the link that carries the device (`route`). The link keeps every device of its kind found in this run in its key of the app state `device.status` (`candidates`; [ADR 0069](../decisions/0069-recording-devices-and-bridge-beside-the-bus.md): app state, never in a journal), with the link that sees each and its signal strength (`rssi`, dBm; `SharedBleScan` reports a device again once its name arrives, its signal moved by 5 dB, its advertising data brings a new key, or a key's bytes change for the first time, and every device still heard at least every 5 s, `BLE_SCAN_REPORT_INTERVAL_MS`), drops a device from the list once its link scans and has not reported it for 15 s, or at once when the scan says it `vanished` (the companion's removed dummy devices; the device the link holds stays and reconnects), connects the first one, and keeps scanning only while it has no device or while a device setup is open (the service `device.discover`). Whenever the links that scan change (a scan starts, ends, or fails, as when Bluetooth is off) it sets them as `scanning` of its status (in the order started, empty when none scans). The rider's calls of the services `device.connect` (another device, or the same one again) and `device.forget` (the device is let go and no device of the kind connects on its own until a device setup opens again, then the best device found does; the rider can connect one meanwhile) go to the links of that kind (keyed by `device.status`: one key per link, `<plugin id>/<kind>/<n>`; a device made of several parts has one key for all of them, ADR 0089); the rider switches links by connecting the device found over the other link. **The choices outlast the run** ([ADR 0054](../decisions/0054-plugin-settings-and-remembered-devices.md)): each link keeps a settings document (`ctx.settings.machine`, `config/machine/<plugin>/device-<kind>.json`) with the device that connected last, by link and its id on the link, or "forgotten". After a restart a remembered device is the only one of its kind that connects on its own, as soon as its link sees it; a forgotten one keeps every device of the kind from connecting on its own until a device setup opens. `remembered-device.feature`, `device-choice.feature`, `device-links.feature` and `same-device-over-both-links.feature` cover it. **Battery level:** on every connection the link reads the Battery Level (0x180F / 0x2A19, one byte in percent) and subscribes to it where the device allows, for every kind; each value is the link's status `batteries` (app state): one entry without `part`, or one per part of a device made of several (ADR 0089). A device without the service tells none. The status gives the levels only for the device that told them; the device details show the weakest on the card and, for a device of parts, every part's below (`battery-level.feature`, `device-details.feature`).
- **Devices made of several parts** ([ADR 0089](../decisions/0089-a-device-made-of-several-parts.md)): `startBlePartsLink` of `@ridrs/ble-peripheral` runs one link per part (the same lifecycle as `startBlePeripheralLink`) and presents them as one device: one key of `device.status`, one settings document with every part (`loadDevicePartsMemory`, version 2; the documents of one link per part from before are merged once), one `device.connection-changed` per state of the device, naming the id of each part (`parts`; the raw inputs carry those ids, a replay maps them). The devices found are offered as devices of all parts: per link the strongest device of each part together, a part's side read by the plugin from the advertising data (`partOf`). Connect and forget take every part; the device is `connected` once every part is, until then `connecting` or `reconnecting` with `missingParts` in its status. The device takes the id of the part found first and keeps it while remembered.
- **Zwift Ride** (`device-zwift-ride`): the pair of controllers is one device made of two parts, `left` and `right` ([ADR 0089](../decisions/0089-a-device-made-of-several-parts.md)): they are two devices with the same name and service `fc82`, the first byte of Zwift's manufacturer data (`094a`) says the side (0x08 left, 0x07 right), and the left one forwards the right one's buttons but not the other way round. Each link subscribes to its notifications (`00000002-19ca-…`) and then writes "RideOn" to its control point (`00000003-19ca-…`), on every connection: the controller sends its buttons only after that. Keypad status packets (opcode `0x23`, a protobuf message read with `@bufbuild/protobuf`, ADR 0040) become `controller.buttons-changed` under the pair's id (the buttons held down on either controller, a button both tell once, published only when that set changes; a controller of a recording from before the pair stands for itself); battery, heartbeat and other packets are ignored, a truncated keypad packet is `malformed-packet`. A pair that is not connected any more releases the held buttons. Its kind is `controller`. The handshake is the `handshake` option of `@ridrs/ble-peripheral`'s link, so `BleConnection` gained `write` (Write Without Response) in every central: Tauri (`ble_write`), noble, the companion bridge (`write` / `written`, protocol 1.1) and the simulator.
- **`@ridrs/metric-source`** (`packages/metric-source`, AGPL-3.0-or-later): the shared logic of `metric-power`, `metric-cadence` and `metric-heart-rate` (three plugins, three manifests, one implementation). Unchanged from Phase 2: the active-source rule, `multiple-sources`, `disconnected` handling, never inventing values, `latest()`. New: every accepted measurement of the active source goes into the metric's temporal series; a source change resets the series, a lost device marks it disconnected, and the metric goes `unavailable` / `stale` when the series turns stale - after a silence that fits the source's rate instead of a fixed 3 s (see [temporal-data-layer.md](temporal-data-layer.md)). Late or duplicate measurements change nothing.
- **Units and reasons**: `MetricUnit` adds `bpm` and `W/bpm`; `MetricUnavailableReason` adds `insufficient-data`, used only by derived metrics while warming up.

### Derived metrics

A derived metric requires only metrics and reads their series; it never subscribes to `measurement.*` and imports nothing device-, BLE- or UI-related (enforced by `dependency-cruiser`). Its `available` readings use the **plugin id** as `deviceId` and the snapshot time `t` as both `measuredAt` and `receivedAt`.

`metric-power-heart-rate-ratio` combines `metric.power` and `metric.heart-rate`. For each snapshot at `t`: if either input is unavailable at `t`, it publishes `unavailable` with the power reason if power is unavailable, else the heart-rate reason (`out-of-range` becomes `insufficient-data`); else it takes both 10 s time-weighted averages at `t`; below 80 % coverage it is `unavailable` / `insufficient-data` ("warming up"); else it publishes `average power / average heart rate` in W/bpm. When an input metric publishes `unavailable`, the ratio follows at once with that reason. Available readings are published once per snapshot; an unavailability only when it changes.

## Phase 9: raw device data

`@ridrs/ble-peripheral` accepts every notification as the input `device.raw-notification` `{ deviceId, deviceName, serviceUuid, characteristicUuid, data /* lowercase hex */, receivedAt }` (`ctx.inputs.accept`), malformed packets included, and decodes it in that input's turn; connection states are inputs too ([time-and-scheduling.md](time-and-scheduling.md)). The link runs in the device plugin's context, so `source` names the decoder that consumed the bytes. No device plugin publishes raw data itself, and decoding is unchanged. Recordings store these events; a replay feeds them through the current decoders ([recording-and-replay.md](recording-and-replay.md)). Phase 8 will add `device.raw-write` for control-point writes the same way.

## Phase 8: trainer control

`device-ftms-trainer` also controls the trainer when it offers a control point ([ADR 0056](../decisions/0056-ftms-trainer-control.md), [trainer-control.md](trainer-control.md)). The peripheral link gained what that needs ([ADR 0052](../decisions/0052-ble-write-with-response-read-and-indications.md)): `optionalSubscriptions` (the control point; `connected` names those subscribed in `characteristics`), `reads` on every connection (each result an input `device.raw-read`), and `write(device, target, data, { withResponse })`, which publishes `device.raw-write` in the turn and writes only while connected; a failed write is the input `device.raw-write-failed`. Notifications of the optional characteristics reach the plugin with their characteristic. A trainer without a control point stays a sensor exactly as before. `control-virtual-gears` shifts on `controller.buttons-changed` of any device.
