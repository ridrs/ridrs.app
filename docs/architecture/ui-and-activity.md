# Activity and UI as Plugins

Phase 3 use case: **I start a ride and see my power and cadence.** The GUI is not an application, it is a set of plugins: a *screen* declares *extension points*, independent plugins *contribute* to them, and the screen never knows its contributors. The HUD is painted **over** the landscape (layers), never beside it.

```text
Smart trainer ──► transport-ble-tauri ──► device-ftms-trainer ──► metric-power / metric-cadence
   (Rust ble.rs via tauri-plugin-blec)        (Phase 2, unchanged)      │ metric.power, metric.cadence
                                                                         ▼
apps/native  (one process: the Tauri WebView)
  PluginHost (bundled plugins) ──► UI registry ──► in-process UiBridge ──► shell
                                                    allow-list,             one screen at a time,
                                                    last-value replay       synced slots
   ├─ screen "main"      ui-main-screen          the layout: places what layout.json names (ADR 0058)
   │     ├─ main/menu     ◄─ ui-main-menu         declares: menu/item   [Today]
   │     │     └─ menu/item ◄─ ui-area-ride, ui-area-training, ui-area-events, ui-area-me (ADR 0059), ui-garage (ADR 0060)
   │     ├─ main/top-bar  ◄─ ui-main-top-bar      "Good evening"
   │     ├─ main/action   ◄─ ui-search, ui-devices (status), ui-settings, ui-area-me (profile)
   │     ├─ main/tile     ◄─ ui-ride-recovery     [Continue ride] [Finish ride] for an interrupted ride (ADR 0057)
   │                      ◄─ ui-tile-ride-start   [Start ride], ride saved
   │                      ◄─ ui-devices           one row per kind, [All devices]
   │                      ◄─ ui-area-ride, ui-area-events, ui-area-me   cards on Today (preview)
   │                      ◄─ ui-training-plan     the next workout
   │     └─ content area  screens ride, training, events, me, search, settings, setup (layout.json)
   └─ screen "activity"  ui-activity-screen      declares: activity/landscape, activity/hud   [Pause|Resume] [Finish ride]
         ├─ activity/landscape  ◄─ ui-landscape-demo     (Phase 10: the world's sensor, publishes ui.terrain-observed)
         └─ activity/hud        ◄─ ui-hud                declares: hud/widget
               └─ hud/widget    ◄─ ui-widget-power, ui-widget-cadence,
                                   ui-widget-heart-rate, ui-widget-power-heart-rate-ratio (Phase 4)

activity-session  (headless)   activity.start-requested / finish-requested → activity.state-changed
```

## Runtime-neutral core

`@ridrs/core` and `@ridrs/contracts` import no `node:*` module and no Node-only library (enforced by `dependency-cruiser`), so the same core runs in Node (`apps/headless`) and in a WebView (`apps/native`). The Node-specific parts sit behind ports:

| Port | Node adapter (`@ridrs/core/node`) | App adapter (`@ridrs/core`) |
|---|---|---|
| `PluginSource` (discovery + module loading) | `createFileSystemPluginSource(dir)` | `createBundledPluginSource({ manifests, modules })` fed by `import.meta.glob` |
| `PluginLogger` (structural, in contracts) | pino | `createConsoleLogger()` |
| ids | `ctx.ids` from the host's `runId` ([time-and-scheduling.md](time-and-scheduling.md)) | same |

Each host leaves out plugins its runtime cannot run: the app bundle excludes `transport-ble-noble` at build time, the headless app disables `transport-ble-tauri` at runtime.

## Manifest `ui` section and UI registry

A plugin declares its UI in the manifest (validated by `uiManifestSectionSchema`, strict):

- `client`: browser module relative to the plugin folder (required with screens, contributions or UI capabilities; may not leave the folder).
- `screens[]`: `{ id, export, extensionPoints? }`. The `id` is the navigation path.
- `contributions[]`: `{ id, extensionPoint, export, order?, extensionPoints? }`. Contributions may offer extension points of their own (nesting).
- `events.subscribe` / `events.publish`: the event ids the client code may use. Their union over all started UI plugins is the bridge allow-list.
- `provides` / `uses`: the UI capabilities the plugin provides (`{ capability, export }`) and the ones its client code draws with `ctx.render` ([ADR 0083](../decisions/0083-ui-capabilities-with-typed-input.md); see [UI capabilities](#ui-capabilities)).
- `state` / `calls`: the app state topics the client code watches and the services it calls ([ADR 0068](../decisions/0068-app-state-and-services-beside-the-bus.md); only on `ui` plugins). Their unions are the registry's `state` and `calls`, the bridge's allow-lists for them.

The core indexes the UI sections of the **started** plugins into a `UiRegistry` (`computeUiRegistry`, pure and deterministic), exposes it as `ctx.ui.registry()` and `host.getUiRegistry()`, and publishes `core.ui-registry.changed` (`{ revision }`) when it changes. It is recomputed once after `host.start()` and after every `stopPlugin` / `startPlugin`, so transient start order never shows up. Contributions are ordered by `order`, then plugin id, then contribution id. Rule violations are diagnostics; the affected entry is left out, the plugin keeps running:

| Code | Situation |
|---|---|
| `unknown-extension-point` | A contribution targets a point no started screen or contribution offers. |
| `duplicate-screen` / `duplicate-extension-point` | Declared twice; the smaller plugin id wins. |
| `client-entry-missing` | The plugin source cannot deliver `ui.client` (no file on disk, or not in the bundle). |
| `client-load-failure` | A client module failed to load or a component threw on mount (reported by the shell). |
| `ambiguous-provider` | Two plugins provide the same UI capability. Like the providers of a `single` capability, all of them are blocked at start, so none is drawn. |

The core never knows what a screen or extension point means and never names one.

## Client contract, shell and bridge

- **`@ridrs/ui-sdk`** (Apache-2.0, imports contracts only): `UiComponent = (container, ctx) => cleanup | void`, the `UiContext` (`events.subscribe/publish` limited to the plugin's own declared events, `slot(point, container, { contribution? })` (with `contribution`, only that one; ADR 0058), `settings` (the plugin's settings documents through the bridge; ADR 0059), `navigate(path)`, `hasScreen(path)` (ADR 0064), `onNavigated(handler)` and `outlet(container, { screens })` for screens shown inside another screen (ADR 0058), `frames.onFrame(handler)` since Phase 7, `onBack(handler)`, and since ADR 0068 `state.watch(topic, listener)` and `call(service, request)`, limited to the plugin's own `ui.state` / `ui.calls`, and since ADR 0083 `render(capability, container, input)`, limited to its `ui.uses`), the `UiBridge` port (with `now()`, the host clock, since Phase 7), and the shared metric display rules (`describeMetricReading`: values rounded half up to their unit's precision - `W`, `rpm`, `bpm` whole numbers, `W/bpm` two decimals; reasons `no source`, `disconnected`, `no signal`, `warming up`).
- **`@ridrs/ui-shell`**: plain DOM, no framework. Renders one screen at a time (`main` first, else the alphabetically first); a screen that the screen in the root took over with `ctx.outlet` is shown in that outlet, with the screen in the root mounted around it; elsewhere, on its own. It mounts each contribution in a wrapper `data-contribution="<pluginId>/<contributionId>"`, keeps slots in sync with the registry without remounting unchanged contributions, and releases everything a component obtained through its context when it unmounts. A component that fails to load or throws is isolated: its wrapper stays empty and the shell reports `client-load-failure`. Navigation is deferred by a microtask, so components may navigate from their own handlers. Since Phase 7 the shell owns the app's one frame clock (`requestAnimationFrame`, or `ShellOptions.frameSource`), see [presentation.md](presentation.md).
- **`@ridrs/ui-bridge`**: `createInProcessUiBridge(host, events)`. Enforces the allow-list (`event-not-allowed`), publishes on behalf of client code with the source `ui-bridge` (payloads validated by the bus: `invalid-event-payload`), and replays the **latest envelope per event** to every new subscriber, so a reloaded or second UI knows the current ride state and metric values. It is created before `host.start()`. App state and services pass it beside the events (ADR 0068): `watchState(topicId, listener)` sends a snapshot message, then the changed keys (`state-not-allowed` outside the registry's `state`), `call(serviceId, request)` calls with the caller `ui-bridge` and passes the answer or the `RidrsError` through (`call-not-allowed` outside the registry's `calls`); `dispose()` ends its watches. See [app-state-and-services.md](app-state-and-services.md).

A remote bridge (the deferred `ui-gateway-web`, WebSocket) would implement the same `UiBridge` port; neither the shell nor any UI plugin would change.

## UI capabilities

A slot offers room and every contribution of its point decides what it shows there. A **UI capability** is the other way round ([ADR 0083](../decisions/0083-ui-capabilities-with-typed-input.md)): the host decides *what* is shown, and exactly one plugin knows *how*. The contracts define it with `defineUiCapability(id, { input, output })` (e.g. `workoutChartCapability`, `ui.workout-chart`); the provider names its export in `ui.provides`, a consumer the capability in `ui.uses`.

```ts
const chart = ctx.render(workoutChartCapability, element, { workout, variant: 'mini' });
chart.onAvailability((available) => { if (!available) element.textContent = '65 min · TSS 72'; });
chart.on('step-focused', ({ stepId }) => select(stepId));
chart.update({ workout: draft, variant: 'edit' });
```

- **Registry:** the core indexes the `ui.provides` of started plugins whose client is available into `capabilities` (`{ pluginId, capability, export, client }`) and each plugin's `uses` into its entry of `plugins`. Two providers of one capability block each other at start (`ambiguous-provider`).
- **Checks in the shell:** `ctx.render` throws `undeclared-capability` unless the capability is in the caller's `ui.uses`. The input is parsed with the capability's schema on `render` and on every `update`; invalid input throws `invalid-request` and the provider sees nothing. The provider's `emit(event, payload)` throws `undeclared-event` or `invalid-event-payload` unless the output schema accepts it, so the consumer's `on` handlers see checked data only. Input and output are plain data: no callbacks, no framework elements.
- **Provider:** `UiCapabilityComponent<C> = (container, ctx, input, emit) => { update, release }`, with its own plugin's `ctx`. `update` gets new input without a new mount.
- **Optional** ([ADR 0053](../decisions/0053-optional-capabilities.md)): while no provider is started, the handle's `available` is `false` and the container is the consumer's, for its own fallback. When the provider starts, the shell empties the container and mounts it with the last input; when it stops, the shell releases it, empties the container and the handle is unavailable again. `onAvailability(listener)` is called at once and on every change, so a consumer has one place for its fallback.
- **Lifetime:** a handle belongs to the component that called `ctx.render` and is released with it, like a slot; `release()` ends it earlier.

**Which mechanism when.** The host decides what is shown and one plugin knows how: a UI capability. The host offers room and any number of plugins decide what to show: a slot. A value that decides a ride (route, workout, targets, gear): the bus, recorded. App data (catalogue, profile, calendar, a draft): state and services. **Ride data is never render input:** a consumer reads it from the bus and at most passes it on, as the HUD passes the workout's progress to the chart. The landscape stays a slot; drawing it through `ctx.render` would lose its route on replay.

`ui-capabilities.feature` covers the mechanism with the fixture capability `ui.test-badge`.

## Keyboard, remote and Back

Every screen of the ride path is usable with the arrow keys, Enter and Back alone (AGENTS.md rule 12, [ADR 0080](../decisions/0080-ride-path-and-workbench.md)): a rider on the bike reaches for a keyboard, a remote or a controller, not the mouse. Workbench screens (editor, import, calendar editing, profile, settings) may need a pointer, but keep the keyboard behaviour below. The shell does it for every screen with `keyboardNavigation(root, { back })` ([ADR 0045](../decisions/0045-keyboard-navigation-tabbable.md)): the arrow keys move the focus through the screen's focusable elements in reading order (Down and Right forward, Up and Left back) and stop at the ends; without focus, the first arrow focuses the first element. The arrows never start over at the top by surprise: when the focused element disappears (a device connected, a list of devices found changed), the next arrow goes on from its place on the same screen, and from a focused element outside the order (`tabindex="-1"`, disabled meanwhile) to its neighbours. Enter keeps the browser's default, which activates buttons and links and submits forms. Text fields keep Left, Right and Backspace for the caret, selects and text areas all arrows. Escape, Backspace, and the back keys of remotes (`BrowserBack`, `GoBack`) are **Back**, and so is Android's back button (`ShellOptions.backButton`; `apps/native` passes Tauri's `onBackButtonPress`, which also keeps Back from closing the app). Keys with Alt, Ctrl or ⌘ and keys a component already handled (`preventDefault`) are left alone.

Back goes to the component that registered `ctx.onBack(handler)` last and is still mounted; without one, Back does nothing (the main screen). `setup` closes the details and puts the focus back on their row, or leaves for `main`; `activity` never ends a ride on Back but moves the focus to Finish ride, which Enter then confirms. Controls show their focus only when they have it (`:focus-visible`), never as a resting look. The companion app has one screen and uses the arrow keys only. `keyboard-navigation.feature` covers it; Android's back button is covered with a fake in `ride-in-native-app.feature`.

## Layering

`ui-activity-screen` stacks its two slot containers absolutely in one stacking context: `activity/landscape` (z 0), `activity/hud` (z 1, `pointer-events: none`), its own **Pause** (or **Resume**, with a large "Paused" while the ride stands still) at the top left and **Finish ride** at the top right (z 2; [ADR 0056](../decisions/0056-pause-and-resume-a-ride.md), `pause-a-ride.feature`). `ui-hud` lays out `hud/widget` in the lower corners and lets pointer events through except on widgets. Screens navigate on `activity.state-changed`, not on clicks: `running` and `paused` lead to `activity` (including the replayed state after a reload), `finished` to the debriefing of `ui-debriefing` when that screen is there (`ctx.hasScreen`; Save or Delete, [ADR 0064](../decisions/0064-ride-debriefing-and-activity-upload.md)), anything else back to `main`. The keep-awake follows `running` only.

## Main screen layout

The main screen is a layout, not content ([ADR 0058](../decisions/0058-main-screen-layout-by-configuration.md)). `ui-main-screen` offers `main/menu`, `main/top-bar` and `main/tile` and places exactly what its `layout.json` names: one contribution in the menu, one in the top bar, and the tiles in order, each in a cell of a 12-column grid with its span (`data-tile`, `data-columns`). A contribution the layout does not name is not mounted; a named one whose plugin does not run, or one that renders nothing, leaves its cell `hidden`. An invalid layout fails the screen. The width of the window decides the breakpoint on the layout's root (`data-breakpoint`): `wide` from 1200 px, `medium` from 768 px (the tiles' medium spans, the menu as an icon rail), `compact` below (no top bar, the menu at the bottom, every tile 12 wide).

The layout sets the design tokens (`--ridrs-bg`, `--ridrs-surface`, `--ridrs-surface-raised`, `--ridrs-line`, `--ridrs-text`, `--ridrs-text-muted`, `--ridrs-accent`, `--ridrs-accent-text`, `--ridrs-info`, `--ridrs-ok`, `--ridrs-warn`, `--ridrs-focus`, `--ridrs-radius`, `--ridrs-gap`) on its root; the menu, the top bar and the tiles draw their own cards with them and may style by `[data-breakpoint]`. A menu entry (`menu/item`) is one `button[data-menu-item]` with `[data-menu-icon]` (its mask in `--icon`) and `[data-menu-label]`; `ui-main-menu` styles them and adds its own Today (formerly Home). The entry of the shown screen is `aria-current="page"` (each follows `ctx.onNavigated`). The screens that `layout.json` names in `screens` (today `setup`) take the place of the top bar and the tiles in the main screen's content area (its outlet), so the menu stays mounted and keeps the focus; the top bar and the tiles are unmounted meanwhile. Those screens do not know the main screen. The other screens stay full-screen with Back. Reading order, and so the arrows' order, is the menu, the top bar, then the tiles, or the menu, then the screen in the content area. `main-screen-layout.feature` and `main-menu.feature` cover it.

## The app's areas (clickable preview)

The menu offers five areas by the rider's intent ([ADR 0059](../decisions/0059-app-areas-as-a-clickable-preview.md), from [main-menu-structure.md](../ideas/main-menu-structure.md)): Today (the main screen) and the plugins `ui-area-ride`, `ui-area-training`, `ui-area-events` and `ui-area-me`, each with a screen and a `menu/item`, followed by the garage (`ui-garage`, [ADR 0060](../decisions/0060-equipment-garage-and-the-frozen-bicycle.md)), which is real, not a preview; the main screen's layout shows their screens in its content area. The global actions sit in the head row beside the top bar, from `main/action` in the order of `layout.json`: Search (`ui-search`), the device status (`ui-devices`, with a dot in the tone of its devices), Settings (`ui-settings`) and Profile (`ui-area-me`); they stay while an area is shown and at the compact width. An action is a `button[data-action]` with an `aria-label`, `[data-action-icon]` and optionally `[data-action-tone]`. The areas put cards on Today (`ride-again`, `next-event`, `weekly-goal`) that can be hidden there and shown again in the area.

**Data sources and the athlete profile ([ADR 0075](../decisions/0075-data-sources-for-the-athlete-profile-and-the-training-plan.md)).** The settings page has a section "Data sources" with a row "Athlete profile": one chip (`pv-chip`, `aria-pressed`) per provider of `athlete.profile`, ridrs on this device first, the chosen one pressed, and the chosen source's status beside it (Ready, Offline · last loaded …, Not available, Loading); a chip calls `data.select`. While a ride is under way the section says that a new source applies from the next ride. The Me area's FTP and weight are the chosen source's: they are shown from `athlete.profile` and changed with `athlete.profile.update` (a refused change says why and leaves the old value; a read-only source disables the buttons; an unset value shows "–" and its first step starts from 200 W or 75 kg). Values the area kept in its own `preview` document before are handed to the profile on this device once by the host side of `ui-area-me`. Today's start card says that the next ride uses default values when the chosen profile is unavailable and has no data. Text of the section and the card is in English and German like all UI text; only the name of a provider other than ridrs comes from the provider.

Most content is a placeholder of the early alpha and marked "Preview" (`[data-preview]`); Go and "Ride … again" start the ride on the demo landscape. Every change is kept at once, without a Save: a client keeps it in a user settings document of its plugin (`ctx.settings.user`, `config/user/<plugin>/<name>.json`), which `UiContext.settings` reaches through the bridge, with the plugin's own permission (`"persistence": ["user"]`). `@ridrs/ui-preview` holds what the areas share (`userDocument`, the preview label, page, card, menu entry and action button). `app-areas.feature` and `app-area-changes.feature` cover it.

## Activity session

`activity-session` publishes `{ state: 'idle' }` on start, moves to `running` (new `sessionId` from `ctx.ids.next()`, `startedAt` from the injected clock) on `activity.start-requested` to `paused` on `activity.pause-requested` (`reason: 'rider'`) or `activity.interrupted` (`reason: 'interrupted'`, the input a recovery injects), back to `running` with `resumedAt` on `activity.resume-requested`, and to `finished` on `activity.finish-requested`, from running or paused ([ADR 0056](../decisions/0056-pause-and-resume-a-ride.md)). Any other transition is an `invalid-transition` diagnostic with no event. A ride never needs a trainer.

## Phase 4 widgets

`ui-widget-heart-rate` (`widget-heart-rate`, bpm, order 2) and `ui-widget-power-heart-rate-ratio` (`widget-power-heart-rate-ratio`, W/bpm with two decimals, order 3) follow the Phase 3 widgets: same test ids (`value`, `unit`, `reason`, `data-status`), same display rules, one subscribed metric event each. `ride-with-heart-rate.feature` runs `startRidrsApp` with the `simulated-ride` fixture (trainer and heart-rate band).

## Phase 5 widgets

`ui-widget-virtual-speed` (`widget-virtual-speed`, km/h with one decimal, order 4) and `ui-widget-virtual-distance` (`widget-virtual-distance`, km with two decimals, order 5) show the virtual rider of the physics engine (see [physics.md](physics.md)). They subscribe to `physics.state` instead of a metric event, use the same test ids (`value`, `unit`, `data-status`) and show an en dash before the first state. Both round with `formatDecimal` from `@ridrs/ui-sdk`, the half-up formatter `describeMetricReading` uses too; no widget rounds on its own. The activity session starts and stops the simulation through `activity.state-changed`. `ride-with-virtual-speed.feature` runs `startRidrsApp` with the `simulated-trainer` fixture.

## Phase 7: a frame-driven landscape

`ui-landscape-flat` (replaced by `ui-landscape-demo` in Phase 10) subscribes to `physics.state-batch` (and `activity.state-changed`, to log presentation stats at ride finish) instead of `physics.state`. It creates one presentation from `@ridrs/presentation` and moves its lane markings every frame of `ctx.frames` by the presented distance (dash period 8 m). Its SVG exposes `data-distance` and `data-basis`; the lane markings keep `data-position`. The HUD widgets stay on `physics.state` at 4 Hz. `ride-with-moving-road.feature` runs `startRidrsApp` with the `simulated-trainer` fixture and a 60 FPS timer frame source. See [presentation.md](presentation.md).

## Phase 10: the landscape as the world's sensor

The demo landscape lives in the UI: `ui-landscape-demo` owns its model (the course of ADR 0027 and the surface, alternating every 500 m between asphalt and gravel), draws it and tells the host what it shows ahead, so what the rider sees is what the physics rides ([ADR 0044](../decisions/0044-ui-landscape-as-world-sensor-and-spatial-layer.md), amended 2026-11-04).

- **Drawing.** Every frame, at the presented distance, the road from 4 m to 160 m ahead in sections split where the surface changes, asphalt and gravel in different colours (the farthest section reaches the horizon); the lane markings on top, unchanged, with `data-position`. Without a state it draws at 0 m. For tests the SVG (`landscape`) carries `data-surface` (the surface under the rider) besides `data-distance` and `data-basis`, and each section in the `road` group `data-surface`, `data-from`, `data-to`.
- **Reporting.** The raw event `ui.terrain-observed` (declared in `ui.events.publish`, carried by the UI bridge as an input): `{ revision, originDistance, spacing, samples: [{ gradient, surface }] }`, 20 m from the whole metre at or before the presented odometer, 1 m apart. The landscape is mounted only on the activity screen, after the ride runs: on mount it publishes the window from 0 m at once (every ride starts there), then a new one whenever less than 10 m are left ahead of the presented position of the running ride; at standstill nothing. Frames of another session (the bridge replays the last batch of the previous ride) are ignored. `TerrainPublisher` holds the rules, `road-sections.ts` the drawing geometry, `landscape-model.ts` the model; all three are pure and unit-tested.
- **Path.** `world-driver-ui` validates the window and accepts it as `world.terrain-preview`; `spatial-terrain` writes it into `@ridrs/spatial`; the physics reads it there ([spatial.md](spatial.md)). The landscape never writes simulation state (AGENTS.md rule 10): frame timing reaches the physics only through input timing. When frames stop for long (window hidden, app in the background), no window arrives, the physics holds the last sample and reports one `terrain-preview-missing`.
- **Tests.** `ui/demo-landscape.feature` (`@ui`, in-process shell): asphalt to the horizon at the start, gravel after 500 m and asphalt after 1 km with a probe standing in for the odometer, and the window reaching the physics' reader. `apps/ride-on-the-demo-landscape.feature` (`@ui` e2e): one window from 0 m at the ride start and none at standstill, new windows while riding below half left, all accepted. The `terrain-observer` fixture records what the landscape published in the e2e app.

## Devices tile and setup

Device plugins say which kind of device they connect: `kind` (`trainer`, `heart-rate`, `controller`) on `device.connection-changed`, optional so early recordings stay valid. Every device link keeps its status as a key of the app state `device.status` ([ADR 0069](../decisions/0069-recording-devices-and-bridge-beside-the-bus.md)): its latest state, the link that carries the device (`route`), the devices of its kind found (`candidates`), the links it looks over (`scanning`) and the battery level of its device. `ui-devices` merges the keys into one status per kind in kind order (`mergeDeviceStatuses`: the most connected link of a kind stands for it, with the devices found and the links scanning of all its links); a component that mounts later gets every key at once.

`ui-devices` contributes the **devices tile** to `main/tile` of the main screen, the device status to `main/action` (formerly the Devices entry of the menu; ADR 0059), and offers the screen `setup`, which the main screen's layout shows in its content area beside the menu. The tile has one row per kind (trainer, power, heart rate) with the device's name and status in the tone of its state (`data-state` on the row). The trainer measures power too and is the only power source so far, so the power row shows the trainer, the same way as in its own (searching while it is searched for). A row opens `setup` with that kind's details (the row asks through a variable of the plugin's client module, `details-request.ts`, since `navigate` takes no parameters); All devices opens `setup` with its rows. Without any device, the tile offers only "Set up your devices". `setup` shows one row per kind with the device name and a status (`role=status`). Continue, or Done once everything is connected, leads back to `main`; nothing there blocks a ride. Conflicts, "not found" timeouts and the start-up flow of [docs/ux-draft](../ux-draft/README.md) are not part of this yet. `devices-tile.feature` and `device-status.feature` cover it.

The second line of a row is the device's name once one is known, else examples of fitting devices. When more devices of the kind were found, the row shows "+N" beside its title. While a kind searches without a device, its row counts every device of the kind found ("2 found", a forgotten one too) beside the status instead. A click on a row shows its **details** in place of the rows, with a round Back button at the top left (Back keys work like it) and no Continue: at the top right a pill that says whether ridrs looks for devices of the kind ("Searching…" while `scanning` in the kind's status names a link, else "Not searching"); the kind's icon, title and one short sentence on what it is for; then the current device as one card, its top laid out like a device found: icon, name, a line with its link ("Over Bluetooth", "Over companion"; on the power row "Smart Trainer over Bluetooth"), the link's icon and signal bars, and its status as its row has it (the check, the reading such as "72 bpm", held controller buttons); below that only the facts the top does not show, at most two per line and never wrapped (for the companion the reason of its state); a one-line tip while the state needs the rider (searching, reconnecting; for the companion also not reachable with the reason's hint, pairing failed); then Remove (a red button with a bin icon) while the device is connected or tried (`device.forget`: no device of the kind connects on its own until a device setup opens again), Connect once it is disconnected, and "Switch to companion" (or "Switch to Bluetooth") while the current device is seen over the other link too (`sameDeviceAs`); and every other device of the kind found, the strongest signal first when the details open (then the rows keep their order and devices found meanwhile follow) with four signal bars and the icon of its link (Bluetooth for Direct, a phone for Companion), each with Connect (not for the controller pair). A device both links see (`sameDeviceAs`) is one box that names it once: on top its row over this device's Bluetooth, below a quieter line per other link; connecting it over the other link switches the link. Every Connect names its link ("Connect with Bluetooth", "Connect with companion"); the devices the companion found are listed, counted and connectable only while `bridge.state` says `connected`, and a disconnected device of the companion offers no Connect until then. Connect and Remove (and Connect of the companion) return to the rows as well. While `setup` is open it calls `device.discover` on every device link (`active` once the link is known, not when the setup goes), so the device plugins keep looking. With the companion transport running (`bridge.state`), the setup has a **Companion App** row of its own; its details show the companion's name and status in a card like a device's (no warning icon beside its status while it is not connected, in its row neither) with Connect or Try again and Remove, red with a bin icon as for a device (it forgets the companion; the details stay open and show the pairing again; no Disconnect: the phone can disconnect, ridrs forgets), and while nothing is paired the extension point `setup/companion`, where `ui-bridge-pairing` contributes two ways side by side: Scan the QR code, or Enter the code (six digits, the sixth pairs) of a companion found on this Wi-Fi. The device plugins remember the rider's choices across restarts ([ADR 0054](../decisions/0054-plugin-settings-and-remembered-devices.md)). `device-details.feature` covers it.

A controller is optional gear: its row (after heart rate) appears only once a controller was found (its status has a device id), and a controller still searched for does not hold up "Everything is connected". The devices tile keeps its three rows. While a device is connected, its status proves that it works, from the device of that row only: the power row shows the watts of `measurement.power` and the heart-rate row the bpm of `measurement.heart-rate` in place of "Connected". On the controller row, the buttons held down on either controller of the pair (`controller.buttons-changed`) take the place of the check, one badge each with a symbol (arrows ← ↑ → ↓, A B Y Z, + − ⚡ ⏻) and its name for screen readers. The status is right-aligned with its icon last, so all icons stand in one column. `device-setup-proof.feature` covers it.

## Phase 8 widgets and the trainer's control

The ride is controlled with the keyboard alone until keys can be mapped in settings (`ride-controls-keyboard.feature`). The activity screen puts Pause and Finish ride first in reading order, so the first arrow of a ride focuses Pause, never a control that changes the ride. One place of the HUD shows what the rider steers with: `ui-widget-erg-dispatch` (`hud/widget`, order 7) mounts the contributions of `hud/erg-off` while ERG is off and those of `hud/erg-on` while it is on, following `trainer.target-power` and knowing neither widget. `ui-widget-virtual-gear` (in `hud/erg-off`) shows the gear ("12 / 24"; with a bicycle's drivetrain the gear large and "50 × 17" below, [ADR 0060](../decisions/0060-equipment-garage-and-the-frozen-bicycle.md)) from `drivetrain.gear-changed`; once there is a gear it takes the focus (`role="spinbutton"`), and while it has it ↑ shifts one gear harder and ↓ one easier: it publishes `drivetrain.shift-requested`, which `control-virtual-gears` handles like a shift button. `ui-widget-target-power` contributes the ERG toggle (`aria-pressed`, `hud/widget`, order 8): Enter turns ERG on at 150 W and off again, and it says only "On" or "Off"; and the target power (in `hud/erg-on`, a `spinbutton` "Target power"): "150 W", ↑ and ↓ change it by 5 W while it has the focus, and Back leaves ERG while it has the focus (registered with `ctx.onBack` only then; otherwise the screen's Back holds). On both, ← and → still move the focus, and while one has the focus and takes ↑ and ↓ it shows them ("↑ ↓ shift", "↑ ↓ target"). Without the focus, + and - (and `=`, + without Shift) anywhere on the screen change the target in ERG and shift the gear otherwise; keys with Alt, Ctrl or ⌘ and keys in text fields are left alone. The ERG toggle and the target only ask: it publishes `trainer.erg-requested`, which the driver `control-erg` turns into the input `trainer.target-power`; it shows the target from that input. The details of a connected trainer in `ui-devices` show its control in one line from `trainer.control-changed` ([trainer-control.md](trainer-control.md)).
